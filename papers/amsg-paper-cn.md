# AMSG：面向真实移动应用的主动空间图谱——以自进化页面-动作图谱弥合小型 GUI 模型的长任务导航缺口

**AMSG: Active Mobile Spatial Graph — A Self-Evolving Page-Action Graph for Long-Horizon Navigation of Small GUI Models in Real-World Mobile Apps**

## 摘要

可端侧部署的小型 GUI 模型具备精确的指令落地（grounding）能力，但缺乏长程规划能力：在弹窗、广告与 A/B 测试构成的高干扰真实移动应用环境中，长任务执行极易迷失。将页面-动作关系组织为图谱以提供导航先验是一条有效路线，但现有图谱方法存在三个根本缺陷：图谱静态冻结，应用迭代使边失效而系统不自知；边仅为布尔存在性，同一操作的多种结果被无差别存入；图谱与 VLM 的控制边界一刀切，或始终检索增强而不节省调用，或直接接管导航而无回退。为此，本文提出主动移动空间图谱（Active Mobile Spatial Graph, AMSG），一种"活的"页面-动作图谱导航方法：（1）自动持久化的活图谱——在线学习持续吸收成功任务的执行观测，统计驱动的自修复降级应对 UI 漂移；（2）边级成功率追踪与 hypothesis（假设）→candidate（候选）→promoted（晋升）→demoted（降级）四阶段生命周期——以统计可靠性替代布尔存在性，仅统计达标的边对智能体可见，并以 t+1 延迟后条件验证（以"实际到达哪"而非"以为会到哪"为事实来源）作为全部统计的真实性根基；（3）锚定性（groundedness，指转移能否脱离当前屏幕内容、由图谱机械完成）分类逐边划定图谱与 VLM 的控制边界——锚定且可靠的边走跳过 VLM 的快速路径，非锚定的边永远保留 VLM 决策。AMSG 配套可复制的陌生 App 五阶段建图管线与跨应用泛化机制，已在淘宝与京东（含秒送外卖链路）两个真实应用上完成核心链路的功能性端到端运行验证；系统性量化评测框架见第 4 章，结果【实验数据待补充】。

**关键词**：GUI 智能体；移动应用导航；页面-动作图谱；在线学习；边生命周期

## 1 引言

视觉语言模型（Vision-Language Model, VLM）驱动的 GUI 智能体，让用户得以用一句自然语言指挥手机完成任务。其中一条对实际部署尤为重要的技术路线，是使用可端侧部署的小型 GUI 模型（如 autoglm-phone-9b 这类 9B 量级模型 [AutoGLM, arXiv 2024]）作为执行器：此类模型经 GUI 专用后训练，能够将一条具体指令精确地落地（ground）为屏幕坐标，且推理成本与隐私属性均适合在设备本地运行。然而，真实移动应用是一个高干扰环境——弹窗、广告、A/B 测试、登录墙与版本迭代使页面形态持续变动，而长任务（如"按预算与规格约束完成一次网购"）要求跨越十余个页面的连贯导航。在这样的环境中，小型 GUI 模型呈现出一种鲜明的能力裂隙：grounding 精确，规划缺位。我们在真机建图实验中观察到（此处为真机观察而非正式实验结论）：小型 GUI 模型能把"点击右上角的筛选按钮"准确 ground 到坐标，却不知道达成"覆盖搜索结果页到筛选面板的转移"这一目标需要点哪个按钮，于是反复徘徊于熟悉的主链路而无法扩展覆盖。换言之，小型 GUI 模型缺少的不是"手"，而是关于应用状态空间的"地图"。

为小型 GUI 模型补上这张地图，图谱化是一条直觉正确的路线。PG-Agent 指出：页面天然构成图，智能体的线性执行轨迹本质上是图上的路径采样，从多条轨迹重建页面图远优于孤立地复用单条轨迹 [PG-Agent, ACM MM 2025]。这一洞察我们完全认同，AMSG 也以其为起点。然而，我们认为以 PG-Agent 为代表的现有图谱方法——包括将 UI 转移图向量化检索的 KG-RAG [KG-RAG, EMNLP 2025]、以交互图直接接管导航的 WebNavigator [WebNavigator, arXiv 2026]，以及基于轨迹记录-重放的 MobiAgent [MobiAgent, arXiv 2025]——共享三个根本缺陷，使图谱在真实移动环境中难以长期可用。

**缺陷一：图谱静态冻结。** 现有方法均从离线收集的数据批量构建图谱，部署后只读不写。但主流商业移动应用以高频节奏持续迭代，按钮移位、流程变更会持续使边失效；由于系统不追踪边的实际执行结果，它既不知道哪些边已经失效，也无法把新页面写回图谱，只能依赖周期性的全量重建。

**缺陷二：边的可靠性不区分。** 现有图谱的边仅记录"页面 A 经动作 X 可达页面 B"这一布尔事实。而真实应用中同一动作可能有多种结果——考虑一个假想例：点击"立即购买"可能进入规格选择页、可能被登录页拦截、也可能弹出促销弹窗。布尔边将这些结果全部当作有效转移存入，规划器可能选中一条仅在特定条件下成立的路径而毫无察觉。

**缺陷三：图谱与 VLM 的控制边界一刀切。** 现有方法在"图谱多大程度上接管导航"上走向两个极端：PG-Agent 与 KG-RAG 把图谱仅作为检索增强材料，VLM 仍逐步推理——图谱改善了提示内容却不节省任何模型调用；WebNavigator 则让图谱直接 Teleport 式接管导航——一旦边因应用更新失效便无回退机制。两个极端都忽视了一个事实：并非所有转移都同质，有的可以放心交给图谱，有的必须留给 VLM。

针对三个缺陷，本文提出三条一一对应的洞察。其一，图谱必须是"活的"：智能体的每一步执行本身就是免费的验证数据流，关键在于以"实际到达了哪个页面"而非"以为会到达哪个页面"作为事实来源——由此引出 t+1 延迟后条件验证，即在下一步观测时回头核验上一步转移是否如预期发生。其二，边的价值在于统计可靠性而非存在性，对应的机制是边级成功率追踪与 hypothesis→candidate→promoted→demoted 四阶段生命周期：边须经反复验证方可提升为智能体可见，可靠性下降则自动降级，统计偏移本身即是 UI 变更信号，自修复无需人工干预。其三，页面转移天然分为两类：位置固定、结果确定的机械转移（锚定，如首页到搜索框），与依赖当前屏幕内容的决策转移（非锚定，如在搜索结果中选哪个商品）。据此，控制强度逐边划定：锚定且统计可靠的边走跳过 VLM 的快速路径以节省调用，非锚定的边永远保留 VLM 推理而图谱仅提供方向提示。三条洞察共同把图谱从"静态导航知识库"升格为"自进化的可执行动作库"。

我们将上述设计实现为主动移动空间图谱（Active Mobile Spatial Graph, AMSG），并构建了配套的陌生 App 冷启动建图管线与多 App 组织机制。本文的主要贡献如下：

1. **自动持久化的活图谱。** 提出以在线学习为持续供给、以质量门控制写入的图谱演化机制：成功任务的执行观测经语义去重与审核后自动并入图谱，可靠性下降的边经统计降级自动收缩，使图谱在应用持续迭代下保持可用，并具备无人工干预的 UI 漂移自修复能力（对应第 4 章 RQ1）。

2. **边级成功率追踪、四阶段生命周期与 t+1 延迟后条件验证。** 以 hypothesis→candidate→promoted→demoted 状态机替代布尔存在性边：只有统计上可靠（验证次数与优势比达标且非高风险）的边才对智能体可见，从根本上避免偶发转移污染规划；并以 t+1 延迟后条件验证（以实际到达页面而非预期到达页面为事实来源）作为全部成功率统计的真实性根基（对应第 4 章 RQ2）。

3. **锚定性分类的图谱/VLM 控制边界。** 每条边独立决定控制强度——锚定边走快速路径节省 VLM 调用，非锚定边保留 VLM 决策——避免"永远 RAG"与"永远 Teleport"两个极端（对应第 4 章 RQ3）。

4. **可复制的陌生 App 建图管线与跨 App 泛化机制。** 提出"引导→焦点探索→staging→人工审核→hypothesis 入图"五阶段管线，其中探索阶段采用强 VLM 规划与小型 GUI 模型执行分离的架构以补足小型 GUI 模型的规划缺位；配合多 App 单库逻辑分区与同域结构先验，使同一领域的新 App 可按相同流程从零完成建图并获得冷启动方向感（对应第 4 章 RQ4）。

系统已在淘宝（核心购物流程）与京东（核心流程及秒送外卖链路）两个真实应用上完成核心链路的功能性端到端运行验证（冷启动建图入库与核心购物任务跑通）；系统性量化评测见第 4 章。本文余下部分组织如下：第 2 章回顾相关工作并定位 AMSG 与现有图谱方法的差异；第 3 章详述 AMSG 的图谱表示、运行时集成、在线学习与生命周期机制，以及陌生 App 建图管线；第 4 章给出实验设计与结果；第 5 章总结全文并讨论局限。

## 2 相关工作

本章按四条主线回顾相关工作：移动 GUI 智能体的总体谱系（§2.1）、图谱与结构化记忆驱动的导航方法（§2.2，与本文最直接相关）、智能体经验复用与记忆机制（§2.3），以及 GUI 智能体评测体系（§2.4）。每条主线末尾给出与本文工作的关联评述。

### 2.1 移动 GUI 智能体

移动 GUI 智能体研究大体沿两条路线演进。**框架路线**以通用 LLM/VLM 为底座，靠外围工程结构补足能力：[AppAgent, CHI 2025] 通过自主探索与人类演示为每个应用构建元素级知识文档，部署期查阅文档执行任务；[Mobile-Agent, arXiv 2024] 以 OCR 与检测定位实现纯视觉感知，摆脱对系统 XML 元数据的依赖；[Mobile-Agent-v2, NeurIPS 2024] 进一步引入规划、决策、反思三智能体协作与任务内记忆单元，缓解长程导航中的历史漂移。这一路线的共性局限在于：知识载体多为非结构化文本或仅在单任务生命周期内有效的记忆，缺少对应用状态空间的持久化结构建模。

**基座模型路线**则直接训练 GUI 专用的视觉语言模型：[CogAgent, CVPR 2024] 以双分辨率编码器支持高分辨率界面元素识别；[UI-TARS, arXiv 2025] 将统一动作空间与 System-2 式反思内化于端到端模型；[AutoGLM, arXiv 2024] 以中间接口分离规划与定位，并采用自进化在线课程强化学习；[Mobile-Agent-v3/GUI-Owl, arXiv 2025] 通过大规模后训练与云端虚拟环境自进化，在 AndroidWorld 上取得领先成绩。此外亦有以验证器替代生成器的尝试，如 [V-Droid, arXiv 2025] 让 LLM 对动作候选打分。

**评述**：基座路线依赖大规模后训练提升能力，数据与算力成本高，且能力提升内化于参数、难以审计与增量修正；框架路线的外围知识又普遍缺少结构与可靠性度量。本文不修改模型参数，而以外置的结构化页面-动作图谱在推理期增强小型 GUI 模型，与基座模型路线正交、可叠加于任意执行器之上。

### 2.2 图谱与结构化记忆驱动的导航

将环境结构显式建模为图谱以辅助导航，是与本文最接近的研究方向。本小节逐一辨析最近邻的四项工作及两项早期代表。需要说明的是，以下对各方法机制的概括基于其公开论文描述与公开实现，细节以原始文献为准。

**[PG-Agent, ACM MM 2025]** 提出自动管线将顺序执行轨迹转化为页面图——经页面跳转判定、节点相似性检查与图更新三步构图——并以 RAG 检索图中的感知指南辅助多智能体执行。其"页面天然成图、线性轨迹是图上路径采样"的直觉与本文一致，是本文承认并继承的起点。但据其论文描述，该页面图为离线一次性构建、在线只读：应用界面更新后边失效而系统不自知，新页面亦无法写回；图中所有边同等对待，仅记录"可达"而不记录"以多大概率可达"；图谱仅作为检索源改善提示内容，VLM 仍需每步推理，并不减少模型调用。

**[KG-RAG, EMNLP 2025]** 将不完整的 UI 转移图（UTG）经 LLM 离线图搜索转化为结构化向量库，在线以 embedding 检索导航路径辅助决策。这一"图谱向量化"路径在检索效率上有优势，但离线扁平化不可避免地损失拓扑结构——检索返回的是文本化路径片段而非可在其上继续推理的图；向量库构建后冻结，同样不追踪边的执行可靠性，也没有对"动作是否真的到达预期页面"的验证环节。

**[WebNavigator, arXiv 2026]** 走向另一个极端：其 Retrieve-Reason-Teleport 范式让离线构建的网站交互图直接控制跨页导航，VLM 只负责页面内操作，并据其论文报告随探索深度增加显著提升成功率。然而 Teleport 隐含"图谱总是正确"的假设——边因站点改版失效时缺少回退机制。更根本地，该方法面向可大规模廉价爬取的 Web 环境；移动应用受登录墙、风控与真机操作成本约束，无法以爬取方式获得高覆盖图谱，其构图前提在移动场景下不成立。

**[MobiAgent, arXiv 2025]** 与其加速框架 [AgentRR, arXiv 2025] 将经典 record-replay 引入智能体：记录交互轨迹并抽象为多级经验（ActTree 结构），重放时由二元匹配模型判断经验是否适用。据其公开描述，"可复用与否"是一次性的二元判断而非边级的连续可靠性度量；经验失效后的更新依赖手动纠正轨迹，亦无对重放结果的后条件验证。

更早的 **[AutoDroid, MobiCom 2024]** 以随机探索构建 UTG 并将探索记忆以文本注入 LLM，但其图谱来自与任务语义解耦的离线随机探索；**[MobileGPT, MobiCom 2024]** 将记忆组织为屏幕—子任务—任务的层级树并支持四阶段复用，但树结构难以容纳跨页面环路与多路径，且依赖 XML 视图层级，对纯视觉输入的智能体不适用。

表 1 从九个维度对比上述最近邻方法与本文提出的 AMSG。

**表 1 图谱驱动导航方法的逐维度对比**

| 维度 | PG-Agent | KG-RAG | WebNavigator | MobiAgent | AMSG（本文） |
|---|---|---|---|---|---|
| 图谱来源 | episode 批量离线构建 | 工具爬取 UTG | 自适应 BFS 爬取 | 任务执行记录 | 引导式探索 + 人工审核 + 在线学习 |
| 图谱更新 | 不更新 | 不更新 | 不更新 | 手动纠正轨迹 | 每次成功任务自动更新 |
| 边可靠性 | 不追踪 | 不追踪 | 哈希去重，无统计 | 二元匹配，不追踪 | 成功率追踪 + 四阶段生命周期 |
| 图谱/VLM 边界 | RAG，VLM 每步推理 | 同左 | Teleport，无回退 | 二元重放 | 逐边独立判定（锚定→图谱 / 非锚定→VLM） |
| 噪声控制 | 双层相似度 | 图搜索评分 | DOM 差分 | 无 | 四道质量门（任务成功 + VLM 审核 + 规范化 + 人工审核） |
| 后条件验证 | 无 | 无 | 无 | 无 | t+1 延迟验证，统计基于真实观测 |
| 自修复 | 无 | 无 | 无 | 无 | 成功率下降→自动降级→重新探索 |
| 跨 App 泛化 | 单 App | 单 App | 单站点 | 单 App | 域模式先验 + 开放词表进化 |
| 探索规划 | — | 爬虫 | BFS | — | 强 VLM 规划 / GUI 模型执行分离 |

**评述**：综观表 1，现有图谱方法在三个维度上集体空缺。其一是**活性**：四者的图谱均在构建后冻结或仅靠人工维护，无法跟随应用的持续更新自我演化；其二是**可靠性度量**：边一律是布尔存在性，同一动作的多种结果（登录拦截、A/B 弹窗）被无差别存入，规划器可能选中仅在特定条件下成立的路径；其三是**控制边界**：图谱与模型的分工要么"永远 RAG"（不节省模型调用），要么"永远 Teleport"（无失效回退），缺少逐转移粒度的边界判定。四者还共同缺少后条件验证：系统记录的是"智能体以为会到达哪里"而非"实际到达了哪里"，即便引入可靠性统计也缺乏事实根基。本文以在线学习与生命周期管理的活图谱、边级成功率追踪，以及锚定性驱动的逐边控制边界回应这三重空缺，并以 t+1 延迟后条件验证为全部统计提供真实性基础。

### 2.3 经验复用与记忆机制

更一般的智能体经验复用研究为本文提供了另一参照系。[AWM, arXiv 2024] 从历史轨迹归纳可复用 workflow；[Synapse, ICLR 2024] 以状态抽象后的完整轨迹作为 few-shot 范例并按相似度检索；[ExpeL, AAAI 2024] 将经验提炼为自然语言 insight 在推理期召回；[Voyager, TMLR 2024] 开创以可执行代码为技能单元的技能库路线；在移动场景中，[Mobile-Agent-E, arXiv 2025] 以 Tips 与 Shortcuts 两类扁平条目实现长期记忆自进化，[AppAgentX, arXiv 2025] 则从重复轨迹中抽象高阶动作以压缩执行步数。

**评述**：上述方法的复用单元——workflow、轨迹范例、语言规则、代码技能、扁平条目——本质上都是线性序列或无结构条目，其共同上限在于复用以"存在一条整体相似的历史经验"为前提：新任务若与任何历史轨迹整条都不相似，即无经验可用。本文将多条轨迹融合进同一全局图谱，复用粒度降至边与子路径——新任务可以走一条从未整条出现过、但每段都被独立验证过的组合路径，从而把经验复用从"轨迹匹配"提升为"图上规划"。

### 2.4 GUI 智能体评测

评测体系方面，[AitW, NeurIPS 2023] 以 71 万余条人类演示建立了离线动作匹配评测的事实标准，但静态匹配无法度量真实环境中的闭环成功率；[AndroidWorld, arXiv 2024] 提供可参数化任务与系统状态奖励信号的在线 Android 环境，是当前最主流的在线基准，但任务集中于开源与系统应用；[AndroidLab, ACL 2025] 在统一动作空间下支持 LLM 与多模态模型的可复现评测，也是本文执行器所属模型体系的训练评测环境；[SPA-Bench, arXiv 2024] 覆盖 340 个中英文真实第三方应用任务并引入成本、耗时等多维指标；[ScreenSpot-Pro, ACM MM 2025] 则显示当前最强模型在高分辨率专业界面上的元素定位准确率仍然很低，直接支撑了本文"小模型 grounding 远未解决、需要系统级结构兜底"的动机。

**评述**：现有基准或为离线静态匹配，或集中于干扰较少的开源应用，普遍缺少中文电商类高干扰、多约束、长程导航任务——而这恰是图谱式导航记忆价值最大的场景。这一空缺构成本文第 4 章在真实商业应用上自建真机评测的依据。

## 3 方法

本章阐述 AMSG 的设计。3.1 节给出问题的形式化设定与总体架构，并说明三项核心设计决策如何逐一回应第 1 章所述三个缺陷；3.2 节定义图谱的表示层——语义页面状态、语义动作节点、领域模式与多 App 组织；3.3 节阐述运行时集成，即锚定性边界划分与图谱如何赋予智能体空间感知；3.4 节给出在线学习机制、边生命周期与自进化闭环；3.5 节描述面向陌生 App 的五阶段建图管线。贯穿全章的有两条设计不变量：其一，**没有任何原始动作被直接写入 Neo4j**——一切观测在进入正式图谱前必须通过相应的质量门（在线路径见 3.4，离线路径见 3.5）；其二，**人工批准不豁免在线验证**——即便经人工审核入图的边，也仅以 hypothesis 阶段存在，对智能体不可见，直至其在线执行统计达标。这两条不变量共同保证：图谱中每一条对智能体可见的边，其可靠性都建立在经过验证的真实执行统计之上，而非建图者（无论是模型还是人）的单方面断言。

### 3.1 总体设计

**问题设定。**我们将一个移动 App 的可达状态空间建模为页面—动作二部图。在 Neo4j 中，其基本模式为：

```
(UIState) -[NEXT_ACTION]-> (Action) -[PRODUCES]-> (UIState)
```

其中 UIState 节点表示一个语义抽象的页面状态（定义见 3.2），Action 节点表示一个语义层面的可执行操作，NEXT_ACTION 关系表示"该页面上存在此操作"，PRODUCES 关系表示"该操作产生此目标页面"。在此模型下，一次任务执行对应图上的一条路径：从入口页面节点出发，经一系列 (Action, PRODUCES) 转移到达任务目标页面。智能体的每步执行循环可抽象为五个阶段：**截图**（感知当前屏幕并分类页面类型）→ **定位**（将当前观测匹配到图谱节点）→ **调度**（依据图谱上下文决定本步由快速路径还是 VLM 推理产生动作）→ **执行**（在设备上施加动作）→ **验证**（在下一步开头核对实际到达页面与预期后条件，即 t+1 延迟验证，详见 3.3.4）。任务执行因而成为"在图上行走、同时为图累积统计证据"的过程——这正是 AMSG 区别于只读图谱方法的结构性前提。

**三项设计决策。**针对第 1 章归纳的现有图谱方法三个根本缺陷，AMSG 逐项作出对应的设计决策。其一，针对**静态冻结**缺陷，采用**自动持久化的活图谱**：图谱不是离线一次性构建的产物，而是随每次成功任务自动生长、随可靠性统计下降自动收缩的在线结构（机制见 3.4）；离线建图管线（3.5）仅解决冷启动，不构成图谱的最终形态。其二，针对**边的布尔存在性**缺陷，采用**边级成功率追踪与四阶段生命周期**：每条边携带真实执行统计，并在 hypothesis → candidate → promoted → demoted 的状态机中流转，只有统计上可靠的边才对智能体可见（3.4）。其三，针对**图谱/VLM 边界一刀切**缺陷（即 2.2 节评述的"永远 RAG"与"永远 Teleport"两个极端），采用**锚定性分类**：每条边独立标注其转移是否可由图谱机械完成，逐边决定控制强度（3.3）。

**总体架构。**图 1 给出 AMSG 的总体架构（图 1，总体架构，待绘）。系统在逻辑上分为三层。**表示层**定义图谱存什么：语义页面状态及其去重签名、语义动作节点、作为结构先验的领域模式、多 App 单库逻辑分区（3.2）。**运行时层**定义图谱如何被消费：统一定位入口、Dijkstra 路径规划与 RuntimeDAG 缓存、锚定性驱动的调度边界，以及 t+1 延迟后条件验证（3.3，验证机制见 3.3.4）。**学习层**定义图谱如何演化：质量门控的自动持久化、边生命周期与自修复（3.4）——该层消费的成功/失败观测流即由 3.3.4 的延迟后条件验证产生。供给与消费在结构上是分开的：离线建图管线（3.5）与在线学习（3.4）是图谱的**两条独立供给线**，各有独立的质量门；但二者产出的边汇入**同一套生命周期消费线**——无论来源是探索审核还是任务执行，新边一律以 hypothesis 入图，经统一的在线验证统计才能晋升为智能体可见、可执行的知识。这一"双供给、单消费"结构是前述两条不变量的架构化体现。

### 3.2 图谱表示

#### 3.2.1 语义页面状态与去重签名

UIState 节点不存储截图或截图哈希，而存储一个语义元组：

```
PageState = (app, page_type, landmarks, affordances, slots, risk_level)
```

其中 `app` 为应用标识，`page_type` 为页面类型（如 `search_result`、`product_detail`），`landmarks` 为页面地标元素集合，`affordances` 为可操作项集合，`slots` 为页面携带的任务槽位，`risk_level` 为风险等级标注。放弃截图哈希的理由是复用性：在购物 App 中搜索"iPhone"与搜索"耳机"，两次截图在像素层面完全不同，但页面结构相同（搜索栏 + 商品列表 + 筛选按钮）。若以截图哈希去重，每次搜索不同关键词都会产生新节点，图谱持续膨胀却无法复用任何导航知识；而以 `(app, page_type)` 级别的语义抽象建模，同一个 `search_result` 节点即可在所有购物任务中复用。去重依靠确定性语义签名 `app|domain|page_type|landmarks|affordances|slots`（实现定位见附录 A）：签名相同的观测被合并到同一节点。签名的确定性（同输入必同输出，不依赖任何模型推理）保证了去重行为的可复现性。

#### 3.2.2 语义动作节点

Action 节点同样以语义而非坐标为身份：

```
Action = (type, intent, semantic_target, postcondition, lifecycle_stage)
```

其中 `type` 为动作类型（Tap、Type 等），`intent` 为语义意图（如 `open_search`），`semantic_target` 为目标元素的语义描述，`postcondition` 为预期到达的页面类型，`lifecycle_stage` 为该动作所处的生命周期阶段。坐标不参与节点身份："点击搜索按钮"在不同分辨率、不同设备上的坐标各不相同，但语义完全一致——若以坐标为身份，同一意图会在跨设备场景下裂解为多个节点。坐标仅作为 `target_locator` 属性附加在动作上，充当锚定证据（其在快速路径中的使用见 3.3）。动作去重键为 `source_page_type|intent|semantic_target|region|target_page_type`，确保坐标不同但意图相同的观测合并为同一动作。在关系层面，每条边记录执行统计：`frequency`（成功次数）、`fail_count`（失败次数）与 `confidence`（成功次数占总次数之比）。本节只界定这些统计**存什么**；它们如何被 t+1 延迟验证更新、如何驱动生命周期流转，留待 3.4 阐述。

#### 3.2.3 领域模式：结构先验与开放词表

图谱不是无约束生长的。领域模式（domain schema，购物域实例为 shopping.yaml）为购物场景定义了结构先验：页面类型词表及各类型的风险等级与典型地标、典型转移集合、探索覆盖目标、危险动作词表（按 common → 域 → App 三级累加）、干扰页面集合（dialog/permission/login/ad/captcha）、陷阱词表，以及默认探索任务模板（以 `{app}` 占位，一份任务文本服务整个领域）。模式的职能是**规范化**（如将分类器输出的 "detail" 归一为 `product_detail`）与**风险标注**（如 `checkout` 始终标为高风险），而非限制图谱生长——图谱可以学到模式未预定义的转移，只要其通过质量门。页面分类器的系统提示词完全由模式生成，因此模式扩展可直接改变分类行为而无需修改代码。

封闭词表是跨 App 泛化的瓶颈：真机测试中，外卖商家页曾被分类器强行归并为词表内最接近的 `product_detail`，造成系统性的页面误判。这一案例催生了**开放词表**机制：分类器遇到词表外的页面时，输出 `new:<类型名>` 加一句话定义，进入提案池；提案出现不少于 2 次才浮出供审阅，且**永不直接建边**，须经人工审核后合入域模式或 App profile。与之配套的模式可扩展性已有定性佐证：为 shopping.yaml 增加即时零售类型（`channel_home` 频道首页、`shop_list` 商家列表及 `store` 的覆盖扩展）后，京东秒送的外卖链路无需修改任何代码即被正确分类——该证据直接验证的是"分类器提示词完全由模式生成"这一模式驱动设计的可扩展性，开放词表则为此类词表外页面提供发现与提案通道。模式因而是一个带先验、可进化的词表：先验把图谱噪声控制在可接受范围内，开放词表让领域边界随真实 App 形态扩张。

#### 3.2.4 多 App 组织：单库逻辑分区

多个 App 的图谱不拆分为多个 Neo4j 库，而在单库内按 `app` 属性逻辑分区。三个理由：其一，跨 App 结构迁移的聚合查询（泛化能力的核心支撑，见 3.3 的同域结构先验）在单库内是一条 Cypher 语句，多库方案则需 Neo4j Enterprise Fabric；其二，节点本就携带 `app` 属性，查询天然按 App 作用域收敛；其三，单驱动连接池，无需维护 App 到库的路由层。App 身份由应用注册表（AppRegistry）统一管理：包名、中英文名与历史编码变体均映射到规范 `app_id`，再映射到所属 `domain`。每个节点写入三个字段——`app`（规范 id，如 `jd`，所有程序检索的作用域键）、`app_raw`（注册表主显示名，如"京东"，供人工浏览过滤）、`domain`（领域，如 `shopping`，跨 App 聚合的分区键）——并建立复合索引 `(app, page_type)` 与 `(domain, page_type)`，保证 App 内定位与跨 App 聚合两类查询均为索引命中。一条来自实践的设计经验：staging 节点与库内已有节点做规范合并后，同一条边的两端可能一端持规范 id（`jd`）、一端持原始值（`京东`），任何以精确相等比较 App 的代码都会静默丢边——因此系统中一切 App 一致性比较必须经由统一的别名感知比较函数完成。

### 3.3 运行时集成：锚定性边界与空间感知

上一小节定义了图谱的静态表示。本节阐述图谱如何在运行期发挥作用：AMSG 不是一个独立于执行器的离线知识库，而是通过 `GraphRuntimeController` 嵌入智能体每步执行循环的在线组件。本节首先提出本文的第三个核心创新——锚定性（groundedness）分类，它在每条边的粒度上划定图谱与 VLM 的控制边界（§3.3.1）；随后介绍承载这一边界的运行时机制：统一定位入口（§3.3.2）与路径缓存（§3.3.3）；接着论证支撑整个统计体系真实性的根基——t+1 延迟后条件验证（§3.3.4）；最后给出多 App 场景下的分层检索与上下文注入设计（§3.3.5）。

#### 3.3.1 锚定性分类：在每条边上划定图谱与 VLM 的控制边界

如第 1 章与 2.2 节所述，现有图谱增强方法在"图谱与模型谁控制导航"这一问题上呈两个极端：或将图谱仅作为 RAG 检索源、VLM 每步仍需完整推理而不节省任何模型调用，或让图谱直接 Teleport 式接管跨页导航、边失效时没有回退机制。两个极端共享同一个盲点：它们不区分"图谱可独立完成的转移"与"必须观察屏幕内容才能决定的转移"。

AMSG 的回答是在**每条边**上标注锚定性：一条边是锚定的（grounded），当且仅当其对应的转移可以由图谱独立执行、无需感知当前屏幕的具体内容；否则为非锚定（ungrounded），必须由 VLM 观察截图后选择具体目标。需注意区分两个同源概念：第 1 章所述"指令落地（grounding）"指模型把一条具体指令映射为屏幕坐标的**能力**，而锚定性（groundedness）是图谱中边的**属性**，刻画该转移可否脱离屏幕内容被机械复现。表 2 以购物域的四条典型转移说明这一区分：

**表 2 锚定性分类示例（购物域）**

| 转移 | 锚定？ | 原因 |
|---|---|---|
| `home → search_input` | 是 | 搜索按钮位置固定 |
| `search_input → search_result` | 否* | 裸 Tap 不锚定（会提交输入框残留文本）；经复合动作合成后才锚定，见正文"机械陷阱类" |
| `search_result → product_detail` | **否** | 选哪个商品取决于当前任务 |
| `product_detail → spec_selection` | **否** | 选什么规格取决于用户需求 |

这一区分来自一个朴素的观察：移动 App 的页面转移天然分为两类——位置固定的**机械转移**（点击搜索框、提交查询、启动应用）与依赖屏幕内容的**决策转移**（在搜索结果中挑选商品、在规格弹窗中选择型号）。前者的正确执行只需要历史上验证过的坐标与操作序列，后者的正确执行原则上无法脱离当前截图与任务语义。把两类转移交给同一种控制方式，要么浪费（对机械转移做完整 VLM 推理），要么危险（对决策转移做盲目重放）。

在实现上，系统以一份非锚定转移清单（实现为硬编码常量，共 9 对页面类型转移，见附录 A）强制划定永不可快速执行的边界，涵盖三类情形：内容决策类（`search_result→product_detail` 选哪个商品、`search_result→store` 选哪家店、`product_detail→spec_selection` 选什么规格、`filter_panel→search_result` 离开筛选需内容决策、`spec_selection→product_detail` 弹窗关闭/取消决策）；购买提交类（`spec_selection→cart`、`spec_selection→checkout`、`cart→checkout`——高风险提交点即使边统计上可靠也永不自动执行）；以及机械陷阱类（`search_input→search_result` 的裸 Tap 会提交输入框中的残留文本，必须经复合动作合成后才可锚定，见下）。此外，**Back/Home 等撤销类动作永不进入快速路径**：撤销属于修复域，图谱无法区分"智能体偏离了路线"与"模型有意绕路"（例如绕开弹窗），自动重放撤销动作会与模型的合理决策相对抗。

锚定性标注存在一个与在线学习交互的细节：`search_input→search_result` 在文档语义上是"输入 + 提交"的复合机械动作，但在线轨迹只会记录到一次裸 Tap。为此动作建议器（ActionAdvisor）从已验证的 Tap 坐标**合成**一条 grounded 的 Compound 提示——`Type <query>` + `Tap 坐标`，其中 `<query>` 槽位在执行时由当前任务计划填充。这一合成使搜索这一最高频的机械步骤真正能走快速路径，而不是因轨迹记录粒度的限制被迫退回 VLM。

锚定性与边生命周期状态（§3.4）共同决定三档调度：

1. **快速路径（Fast Path）**：锚定且 promoted 的边直接由图谱执行，跳过 VLM，单步约 0.5 秒（实测估算）；
2. **Graph Co-pilot**：标注为 `verify_with_vlm` 的转移由图谱给出方向性提示（语义目标、路径概要），VLM 负责在截图上完成具体 grounding；
3. **完整 VLM 推理**：非锚定边或图谱无路由时的默认路径，单步约 5 秒（实测估算）。

快速路径的准入判据为：`grounded=True` 且 `confidence ≥ 0.9` 且（有已验证坐标，或为合成 Compound，或动作类型属于 {Launch, Wait}）。其中置信度阈值 0.9 是设计参数而非调优结果。与前述两个极端对比，AMSG 的控制边界不是系统级的一刀切，而是**每条边独立决定控制强度**：图谱在它确定可靠的机械转移上完全接管以节省模型调用，在依赖内容的决策转移上退为提示者，把 grounding 权威留给 VLM。

#### 3.3.2 统一定位入口：locate_and_get_context()

图谱知识进入执行循环的唯一入口是智能体循环在图谱定位阶段调用的 `locate_and_get_context()`（由记忆管理器委托给图谱运行时控制器 GraphRuntimeController）。该方法在一次调用中完成六步：① 页面匹配——以 `(app, page_type)` 复合键查询 Neo4j 定位当前页面节点；② 验证上一步缓存的 pending transition（见 §3.3.4）；③ 目标推断——从任务槽位（TaskSlots）推导目标规格（GoalSpec，目标 page_type 与槽位约束）；④ Dijkstra 加权最短路规划从当前节点到目标的路径；⑤ 将规划结果缓存为 RuntimeDAG（见 §3.3.3）；⑥ 返回调度模式 `mode` 及候选动作与语义上下文。

返回的 `mode` 直接驱动后续调度决策：

**表 3 locate_and_get_context() 的四种返回模式**

| mode | 含义 | 智能体行为 |
|---|---|---|
| `navigate` | 图谱有路径，下一步可执行 | 锚定边 → 快速路径；非锚定边 → VLM + 提示 |
| `explore` | 图谱无路径（冷启动或覆盖缺口） | 完整 VLM 推理，图谱记录新观测 |
| `verify_with_vlm` | 图谱有方向但需 VLM 选择具体元素 | VLM 推理 + 图谱语义目标提示 |
| `goal_reached` | 当前页面已是目标 page_type | 无需导航动作 |

这一设计把"定位、验证、规划、缓存"压缩为每步一次的原子调用，使图谱对执行循环的侵入面保持最小：智能体主循环只消费一个 `mode` 字段与一组提示，无需理解图谱内部状态。

#### 3.3.3 RuntimeDAG：路径缓存与按需失效

Dijkstra 规划本身在微秒量级完成，但完整定位管线（Neo4j 查询 + 规划 + 上下文组装）每步需 50–200 毫秒（工程量级估算）。考虑到多步导航中相邻步骤通常沿同一条规划路径推进，逐步重复完整管线是纯粹的浪费。RuntimeDAG 将一次规划的结果缓存为内存中的边数组与游标：缓存命中时直接取 `route[current_index]` 返回下一动作，耗时约 10 毫秒（实测估算），不再查询 Neo4j。

缓存的正确性由四项失效条件保证：后条件不匹配（实际到达页面与路径预期不符）、应用切换、连续失败超过阈值、下一步为高风险边。任一条件触发后 DAG 作废，下一步的定位阶段自动重建完整管线。失效是被动且廉价的——系统不试图增量修补过期路径，而是直接重新规划。

RuntimeDAG 有一个副作用需要如实陈述：DAG 可用时，感知阶段跳过页面分类器（PageClassifier）的 VLM 调用，进一步节省一次模型调用；其代价是当弹窗等意外页面出现时，智能体会带着错误的 page_type 多走一步。这个错误不会累积——下一步的延迟后条件验证（§3.3.4）会发现实际页面与预期不符，记录失败观测并触发 DAG 失效与重建。系统在此有意接受"单步延迟发现"，换取稳态下的调用节省，并以验证机制兜底。

#### 3.3.4 t+1 延迟后条件验证：统计真实性的根基

锚定性调度与下一节的边生命周期都建立在边级成功率统计之上，而成功率统计的价值完全取决于其数据来源是否真实。AMSG 以**延迟后条件验证**回答这一问题：智能体在执行动作后的状态更新阶段，将三元组（当前页面，动作，预期目标页面）暂存为 pending transition；下一步（t+1）图谱定位阶段的开头，将页面分类器对新截图给出的实际 page_type 与预期目标对比——匹配则记 `record_observation(outcome="success")`，不匹配则记 failure 并触发修复策略（DAG 失效、回退 VLM 路径等）。

这一机制的必要性可以从反面论证：若没有后条件验证，边成功率的统计来源是"智能体以为这个动作会到达哪个页面"，而非"动作执行后实际到达了哪个页面"。在高干扰的真实 App 环境中，二者系统性地不一致——登录拦截、A/B 实验弹窗、促销浮层都会让同一动作产生预期之外的结果。建立在"以为"之上的成功率是自我报告，建立在"实际"之上的成功率才是经验事实。整个边生命周期系统（hypothesis 的提升、promoted 边的降级、自修复）的正确性都以这一事实流为前提。如 2.2 节表 1 的"后条件验证"维度所示，PG-Agent、KG-RAG 与 WebNavigator 均不具备此类机制：它们的图谱中"边存在"这一事实从建图时刻起便不再接受经验检验。

验证机制本身还需要防御一种隐蔽的退化。一个看似合理的"优化"是把运行时的预期后条件喂给 PageClassifier 作为分类偏置——既然图谱预期下一页是 `search_result`，让分类器倾向这一答案似乎能提高分类稳定性。AMSG 将其确立为一条架构红线，有意识地拒绝：分类器的输出是后条件验证的 ground truth，一旦验证的裁判被验证的预期所偏置，验证就退化为自我证实——预期什么便"看到"什么，失败的边永远不会被记为失败，生命周期统计的真实性随之坍塌。保持分类器对运行时预期的独立性，是统计体系可信的结构性前提，其地位等同于实验科学中测量仪器对假设的独立性。

快速路径执行还配有一道同步后条件检查：快速路径执行器在执行后立即截取新屏并分类，失配时当步回退模型路径并记失败观测，最坏代价是多一次模型调用。同步检查保护单步执行的即时正确性，t+1 延迟验证则覆盖包括模型路径在内的全部转移并供给统计流，二者互补。

#### 3.3.5 多 App 分层检索与同域结构先验

当图谱服务于多个 App 时（§3.2 的单库逻辑分区），运行时检索按三层组织，且**只有第一层产生可执行动作**：

1. **App 专属子图**：前台 App 检测经 AppRegistry 规范化后，所有查询以规范 App id 为作用域。promoted 边的快速路径只能来自这一层——可执行的坐标永远属于当前 App 自己验证过的边。
2. **同域结构先验**：当 App 子图过冷（节点覆盖低于阈值）且 `mode=explore` 时，注入同域其他 App 在当前页面类型上的常见转移——由领域模式中的 schema 转移与跨 App promoted 边聚合而成，按支持度排序。关键约束是这一层**仅作为文本提示进入语义上下文，绝不携带坐标**：其他 App 的 `target_locator` 禁止执行，从机制上杜绝跨 App 坐标污染。其效果可概括为"京东冷启动时复用淘宝沉淀的购物结构先验"——新 App 没有可执行的边，但获得了"购物 App 的搜索结果页通常可进入筛选面板与商品详情"这类结构性方向感。该层可由域先验开关关闭以作消融（开关标识见附录 A）。
3. **common_mobile 兜底**：dialog/permission/login/captcha 等通用干扰页的处置知识，与具体域无关。

图谱知识最终经两条通道进入 VLM 提示：**导航上下文**在 `mode=navigate` 时注入"当前位置 → 目标"的路径概要与下一步动作描述，VLM 可采纳亦可忽略——图谱在此是建议者而非指挥者；**动作提示**由 `ActionAdvisor.query()` 给出当前页面全部 promoted 边的列表，其中非锚定边只提供"该转移存在"的信息而不提供坐标，VLM 必须自行观察截图决定具体目标。两条通道与 §3.3.1 的控制边界一致：坐标级的执行权严格限定在锚定且可靠的边上，其余一切图谱知识都以可拒绝的文本提示形式存在。

每一步执行结束时，后条件验证都会产生一条成功或失败的观测，这正是图谱保持"活性"的数据来源。这条事实流如何被消费、如何驱动边的提升与降级乃至图谱的自修复，是下一节的主题。

### 3.4 在线学习、边生命周期与自进化

前两节解决了图谱"长什么样"（3.2）与"怎么用"（3.3）的问题；本节回答图谱"如何生长"——这是 AMSG 名称中"主动"（Active）一词的实质所在，也对应本文第一、二项核心创新。3.3 节的 t+1 延迟后条件验证为每条边持续产生基于真实观测的 success/failure 计数，本节阐述这一事实数据流如何经由双重质量门、四阶段生命周期与自动降级机制，将一个静态的导航知识库转变为持续自进化、可自修复的活图谱。

#### 3.4.1 自动持久化管线与质量门 1：任务级成败过滤

AMSG 的持久化管线遵循一条贯穿全系统的核心规则：**没有任何原始动作观测直接写入 Neo4j**。任务执行期间，每步产生的页面状态与转移观测全部暂存于内存结构中，同时边生命周期管理器（EdgeLifecycleManager）在内存中更新对应边的成功/失败计数与优势比。按定义，一个 20 步的任务约产生 20 个暂存观测；整个过程不触碰持久化存储。

只有当任务以成功状态结束时，系统才触发 `flush_staged_graph()` 将暂存观测落库；失败任务的全部暂存观测被整条丢弃。这构成第一道质量门，其设计论点是：失败轨迹的观测可能整条都是错误导航——走错路径、陷入循环、被弹窗劫持——写入图谱会系统性污染后续任务的规划。以一个 20 步的失败任务为例，其中多数步骤可能均为错误操作，逐步甄别哪些步骤可信的审核成本高于整条丢弃。任务级的粗粒度过滤因而是一个有意为之的工程取舍，其依据是错误观测的代价不对称：错误观测一旦入图会污染规划、误导后续所有任务，而被丢弃的少量正确观测在下一次成功任务中仍会被再次观测到。

`flush_staged_graph()` 的落库过程分三步。第一步，`canonicalize_state_graph()` 执行规范化与过滤：按语义签名（3.2 节）对页面状态去重，使"搜索 iPhone"与"搜索耳机"得到的结构相同的结果页合并为同一节点；过滤 `unknown` 类瞬态页面；执行应用一致性检查，拒绝跨应用页面间的非法直接转移边。第二步，对每条暂存边执行生命周期提升检查（条件见 3.4.3）。第三步，以 Cypher `MERGE` 语义将页面状态与转移写入 Neo4j——`MERGE` 保证幂等性，重复写入不产生重复节点；边的生命周期元数据（`lifecycle_stage`、`verification_count`、`dominance_ratio`）作为 Action 节点属性同步落库，使生命周期状态跨会话持久。

#### 3.4.2 质量门 2：VLM 轨迹审核

第一道门过滤的是"整条任务级"的噪声，但成功任务内部仍可能混入页面分类器误判产生的虚假转移——典型案例是 `dialog → home`：智能体关闭一个广告弹窗回到首页，被分类器误读为"存在一条从对话框页通向首页的导航边"，这类边一旦入图会误导路径规划。为此，`flush_staged_graph()` 完成后，`TrajectoryReviewer.review_and_import()` 对保存的轨迹 JSON 执行第二道审核：① 提取步骤间的页面转移链；② 过滤同页、`unknown`、`finish`、`wait` 等伪转移；③ 与 Neo4j 现有边比对去重，已知转移不重复处理；④ 将新转移候选提交给强 VLM（经强 VLM provider 链配置，见 4.2 节与附录 A）判定真伪。审核提示词的核心片段如下：

> 你是一个手机 App 页面导航图谱的质量审核员。以下是从执行轨迹中提取的新页面转换。请判断每条转换是否是真实有效的页面导航。
> 有效：从一个明确的页面类型跳转到另一个明确的页面类型。
> 无效：dialog → home（关闭广告弹窗），分类器错误导致的虚假转换。

仅获 VLM 批准的转移以 `lifecycle_stage="hypothesis"` 导入图谱——即便通过审核，它们对智能体仍不可见（3.4.3）。

管线迭代过程中沉淀了两条失败安全（fail-safe）教训。其一，VLM 输出解析失败时，候选必须标记为"未审核"而非默认通过——早期实现采用"解析失败则全部通过"的反向回退，等价于在审核器最不可靠的时刻把质量门完全打开，是危险的失效模式。其二，导入必须以语义键 `MERGE` 而非 `CREATE` 执行——早期 `CREATE` 实现会在审核流程重跑时产生重复 Action 节点，破坏图谱的去重不变量。审核判定逻辑封装为共享组件 `VlmTransitionJudge`，同时服务于此处的在线审核与离线探索数据的批次审核；离线建图管线另设独立的人工审核质量门，见 3.5 节。

#### 3.4.3 四阶段边生命周期

通过双重质量门入图只是边生命的起点。AMSG 用一个四阶段状态机管理每条边从"被观测到"至"可被执行"的全过程（图 2，边生命周期状态机，占位待绘）：

```
hypothesis → candidate → promoted → demoted
                              ↑__________|（重新验证达标后可再提升）
```

各阶段对智能体的可见性如表 4 所示：

**表 4 边生命周期各阶段及其对智能体的可见性**

| 阶段 | 语义 | 对智能体的可见性 |
|---|---|---|
| `hypothesis` | 已观测/已审核，但未经运行时验证 | 不可见，不能用于快速路径 |
| `candidate` | 验证次数达标但结果分布尚不稳定 | 不可见 |
| `promoted` | 统计可靠 | **可见**：锚定边进入快速路径，非锚定边作为 VLM 方向提示 |
| `demoted` | 曾经可靠但成功率坍塌 | 不可见，交还 VLM 重新探索 |

这张可见性表是生命周期设计的要害：**只有 `promoted` 边对运行时智能体可见**，且即使可见，其作用方式仍受 3.3 节锚定性边界约束——锚定边可绕过 VLM 直接执行，非锚定边只提供"该转移存在"的方向性提示。一条边要影响智能体的实际行为，必须同时跨过两道相互独立的门：统计可靠性（生命周期）与控制权限（锚定性）。

提升条件为三项合取：`verification_count ≥ N` 且 `dominance_ratio ≥ θ` 且 `risk ≠ high`，其中 `verification_count` 为 3.3 节后条件验证累积的次数，`dominance_ratio` 为主导结果在全部观测结果中的占比——它比简单成功率更严格，因为同一动作通向多个不同结果页（登录拦截、A/B 弹窗）的边即使"次次有响应"也无法形成主导结果。N 与 θ 为系统设计参数（而非调优结果），其取值须区分三个层次以免混淆：其一，配置数据结构的字段默认值为 N=1、θ=0.6，这只是工程上渐进部署的起点，单次观测即可提升的 N=1 不满足"边须经反复验证方可提升"的设计哲学，不构成本文的实验配置；其二，实现中另提供用于回归对照的 `legacy` 预设，其提升策略沿用旧式布尔逻辑、不执行上述统计门控；其三，本文实验固定采用架构文档推荐的 `sava` 预设（verified 提升策略，N=3、θ=0.8）——本节两条不变量与第 1 章的相应论述均以该预设为前提，N 取值对错误快速路径执行率的影响可作为敏感性分析纳入第 4 章 RQ2。降级条件为：`promoted` 边的优势比跌破 0.4（设计参数）即自动降级为 `demoted`。

生命周期系统维持两条强不变量。**其一，人工批准不豁免在线验证**：经 3.5 节人工审核门批准入图的边同样以 `hypothesis` 起步，必须在真实执行中通过后条件验证累积到达标统计才能提升——人工判断回答的是"这条转移是否真实存在"，而只有运行时统计能回答"它是否可靠到值得绕过 VLM"。**其二，高风险目标边永不成为可执行快速路径**：如 `cart → checkout` 这类购买提交边，可以作为节点间连通性存在于图谱中以保证路径规划的结构完整性，但提升条件中的 `risk ≠ high` 子句使其永远停留在不可快速执行的状态——涉及资金与不可逆操作的转移，无论统计多么可靠，决策权永远保留给模型与上层安全护栏。

#### 3.4.4 自修复：统计偏移作为 UI 漂移信号

静态图谱方法的根本困境在于：应用更新使边失效，而系统对此一无所知。AMSG 的生命周期机制使 UI 漂移的检测与恢复无需任何人工干预，其因果链如下：应用更新导致某条 `promoted` 边对应的按钮功能改变 → 智能体走快速路径执行该边 → t+1 后条件验证发现实际页面与预期不符，记录 failure，同时智能体回退 VLM 路径完成当前步 → 该边的 `dominance_ratio` 随失败累积而下降 → 跌破降级阈值后边被降级，智能体不再使用 → 后续任务中 VLM 对该转移重新探索 → 新观测建立新的 `hypothesis` 边 → 经后条件验证达标后重新提升为 `promoted`。整个闭环中没有"UI 变更检测器"这样的专用组件：成功率的统计偏移本身就是 UI 变更的信号，检测与恢复完全由已有的验证-生命周期机制实现。根据系统开发期的经验估计，该自修复过程通常在 3-5 次任务内完成（正式测量见第 4 章）。

#### 3.4.5 自进化正反馈闭环与收敛性

以上机制组合形成跨任务的正反馈循环（图 3，自进化闭环示意，占位待绘）：成功任务经双质量门为图谱新增或强化转移 → 更多边累积验证统计并提升为 `promoted` → 后续任务中更多步骤命中快速路径 → VLM 调用减少、单任务延迟下降且确定性增强 → 任务更易成功 → 进一步为图谱提供观测。图谱由此不再是被动查询的知识库，而成为随使用自动增值的动作库。

一个自然的疑虑是该循环是否导致图谱无限膨胀。答案是否定的，其根据在于移动应用状态空间的有限性：一个典型购物 App 仅有约 8-12 种核心页面类型与 15-25 种常用转移（经验估计），且语义签名去重（3.4.1）保证同型页面不重复建节点。经验上，约 10-20 次成功任务后核心流程（首页 → 搜索 → 结果 → 详情 → 规格 → 购物车）的转移即基本覆盖，此后的成功任务以强化已有边的统计为主，仅偶尔发现边缘场景的新转移。就延迟而言，系统呈现出从冷启动期（无可用边，全程 VLM 推理）到稳定期（核心机械导航全部走快速路径）的单调改善趋势；稳定期的延迟下界由非锚定步骤决定：选哪个商品、选什么规格这类依赖当前屏幕内容的决策步骤，无论图谱多么完善都必须保留给 VLM，这正是 3.3 节锚定性边界的设计本意。各阶段的量化延迟与快速路径命中率见第 4 章【实验数据待补充】。

### 3.5 陌生 App 的五阶段建图管线

前述运行时检索（3.3 节）与在线学习（3.4 节）均以"图谱中已有可用边"为前提，而在线学习又以任务成功为写入条件——在一个图谱从未见过的 App 上，智能体缺乏空间先验、任务成功率低，由此形成冷启动的循环依赖。本节给出 AMSG 的离线建图管线（对应贡献④）：一条"引导→探索→规范化→审核→入图"的五阶段闭环，将陌生 App 从零图谱推进到核心链路以 hypothesis 边入图的状态。区别于现有工作中一次性的数据集工程（如 KG-RAG 依赖 xTester 离线爬取、WebNavigator 依赖自适应 BFS），该管线设计为可对同域 App 重复执行的流程（其可复制性目前以京东作为单一同域案例得到验证，样本限制的讨论见 4.1 节 RQ4 与第 5 章），且其产物与在线学习共用同一套生命周期消费机制。

管线的全部设计服从两条原则。**原则一：逃逸不依赖 VLM 分类正确。** 真实 App 环境高度干扰——直播间、抽奖弹窗、外跳页随时可能中断探索进程，而此时恰恰是分类器最容易出错的时刻；因此所有逃逸与防御机制必须建立在机械信号之上（截图感知哈希、覆盖进度、前台包名等），分类结果只作参考。**原则二：离线探索产物一律不直写正式图谱。** 探索数据缺乏在线执行那样的"任务成功"质量门，人工审核因而成为离线数据进入图谱前的唯一质量门。整体流程如图 4 所示。

#### 3.5.1 阶段一：App 引导（onboarding）

引导阶段对陌生 App 做安全采样：启动、按 Back、下滑各截取一张截图，全程绝不点击，从源头排除误触风险。强 VLM 据此推断 App 所属领域，产出 **draft profile**（`schemas/apps/<id>.yaml`），内容包括：domain 到领域模式的映射、覆盖建议、该 App 界面语言下的危险词与陷阱词（直播、抽奖、领券类入口）、登录墙标记与建议探索任务。VLM 输出随后经过一个确定性校验层对齐到领域模式（3.2 节）：覆盖类型经别名规范化并剔除干扰类型，越出模式的转移直接丢弃，与购物 CTA 冲突的"危险词"被降级——例如"加入购物车"在购物域是打开规格弹窗的入口而非危险动作，VLM 的保守判断需要被结构先验纠正。最后设人工确认门：draft 状态的 profile 允许驱动探索，但其产物被拒绝入图，人工核对后改为 confirmed 方可解锁。

#### 3.5.2 阶段二：分轮焦点探索

探索阶段是管线的核心，其设计直接回应第 1 章所述的真机观察——小型 GUI 模型（如 autoglm-phone-9b）grounding 精确而规划缺位：它能将"点击右上角的筛选按钮"精确 ground 到坐标，却不知道覆盖 `search_result→filter_panel` 这一目标*需要*去点筛选按钮，自主探索时反复徘徊于记忆中的主链路而无法扩展覆盖。该观察直接导出**规划-执行分离**的架构：强 VLM 规划器每步接收当前截图、剩余焦点转移与最近执行结果，输出一条具体指令（如"点击右上角的'筛选'按钮"）；小型 GUI 模型只接收这一条指令做 grounding 执行，不感知整体探索任务。执行结果回灌规划器（"指令 X 落到 search_result，预期 filter_panel 未达成"），失败则调整探索策略，目标覆盖完毕则主动 finish。两个模型各自只做擅长的事：规划归强 VLM，落点归小型 GUI 模型。

单轮预算有限（每轮 24 步，设计参数），不可能覆盖全部目标，因此探索按**分轮焦点**组织：每轮启动时扫描历届产物的覆盖记录，从缺口中取一个小目标（骨架转移优先），完成即收尾保存，下一轮自动选取下一批缺口。焦点参数 `--focus` 支持结构化形式（`search_result->filter_panel`）与自然语言形式（"探索首页的秒送模块"）混用——后者没有预设转移，由规划器自主发现并判断结束。轮末由强 VLM 生成 round_summary（完成了什么、卡在哪、下轮建议）写入产物，作为跨轮规划的记忆。

探索全程由一个遵循原则一的防御栈守护，其"威胁→机械信号防御"对应关系如表 5 所示。

**表 5 探索防御栈：威胁与机械信号防御**

| 威胁 | 防御（不依赖分类正确性） |
|---|---|
| 直播间/广告页死循环 | 感知哈希滞留检测，逃逸逐级升级（Back→Back→重启 App）；陷阱词进入前拦截并回写负面经验记录 |
| 外跳浏览器/其他 App | 前台包名漂移检测，自动拉回目标 App |
| 弹窗/挽留弹窗 | 消解循环（找关闭按钮→Back→点空白）；Back 被拦截时寻找"退出/离开"语义按钮 |
| 人机验证（captcha） | 列为一等页面类型；默认蜂鸣暂停、人工接力完成后续跑；人工操作不记边 |
| 登录墙 | `--pause-on-login` 人工接力 |
| 加载中间帧被当作页面 | 落页稳定性检测：连续截图相似才送分类 |
| 分类器误判 | 三信号一致性核验（分类器输出/推理证据/landmark 结构）：不一致者按 transient 拒绝或标记 low_confidence 交审核 |
| 中断/崩溃 | 中断安全保存，已采集数据永不丢失 |

表中两项需要展开。captcha 不是异常，而是一等页面类型：用 Back 绕开只是推迟问题，默认策略是蜂鸣暂停交人工接力，且人工操作期间不记录任何边，避免把人类的操作知识误标为模型可复现的转移；三信号一致性则把"单分类器判断"升级为交叉验证，分类结果须与推理证据及 landmark 结构核验一致，否则降级处理——这与原则一一脉相承：分类器只是证据之一，不是裁决者。

#### 3.5.3 阶段三：staging 规范化

每轮探索产物（pages、transitions、轨迹 JSON 与截图证据）自动打包为 staging 批次（`memory_db/staging/<batch>/`）。规范化流程对候选数据做五项处理：基于语义签名（3.2 节）的去重、瞬态页过滤、Type+Submit 搜索宏合成、同页动作压缩、高风险边界过滤。关键约束是：staging 只在磁盘上组织候选，**不接触 Neo4j**——这是原则二在数据通路上的实现，正式图谱在此阶段对探索产物完全不可见。

#### 3.5.4 阶段四：人工审核门

staging 批次经 Gradio 审核界面逐条人工裁决。每条候选边呈现：转移前后截图对、动作描述、观测次数与置信度、VLM 预判，以及**双盲交叉验证**结果——强 VLM 独立重新分类转移两端截图，且不被告知探索时的标签，与探索期标签不一致的候选标红置顶。批次概览呈现完整漏斗：探索记录 N 条、探索期被拒 K 条、进入候选 M 条、当前 approve/reject 统计——任何一条数据的去向都可追溯，不存在静默丢失。为降低审核负担，系统提供决策预填规则：VLM 批准、或观测不少于 2 次且非低置信、或来自人工辅助采集（操作者已亲眼验证两端）的候选预填 approve，其余预填 reject；预填仅是建议，最终裁决权在人。

#### 3.5.5 阶段五：批准入图

批准入图操作将批准的边写入 Neo4j，写入时携带 `lifecycle_stage="hypothesis"` 与溯源属性（来源类型、审核批次标识）。写入遵循 3.1 节不变量二（人工批准不豁免在线验证）：hypothesis 边对运行时智能体不可见，仍须经在线验证统计达标方能提升为 promoted。此外，重复的批准写入由落库回执机制拦截，保证批次写入的幂等性。

**人工辅助采集。** 当自主探索对某些转移无能为力（执行知识缺失）时，操作者或更强的智能体可直接驱动设备采集，产物按同一格式落盘，走同一条 staging→审核→入图管线，仅以 `source_kind=human_assisted` 标记来源。这是给图谱注入"转移→操作"执行知识的捷径：入图后探索器与运行时智能体即可复用，且因其经过同一审核门与同一在线验证，不构成质量上的特权通道。

#### 3.5.6 与在线学习的衔接

离线管线解决的是冷启动；图谱最主要的持续数据来源仍是 3.4 节的在线学习——每次成功任务都可能发现新转移或验证已有转移。两条供给线的质量门相互独立（离线靠人工审核门，在线靠任务成功门与 VLM 轨迹审核），但汇入同一套生命周期消费机制：无论来源如何，所有边都从 hypothesis 起步，靠真实执行统计赢得 promoted 地位。这一管线的可复制性已有单案例的定性佐证：京东（含秒送外卖链路）从零图谱到核心链路入图即按此五阶段流程完成；探索期间为领域模式补充的即时零售页面类型（`channel_home`、`shop_list` 及 `store` 的覆盖扩展）反哺整个购物域——由于分类器提示词完全由模式生成（3.2.3），后续同域 App 无需任何代码改动即可正确分类同类页面。该扩展验证的是模式驱动提示词的可扩展性；开放词表机制（3.2.3）则为词表外页面提供发现与提案通道。

## 4 实验

本章给出 AMSG 的评测框架。实验设计的核心原则是"研究问题与创新主张一一对应"：第 1 章提出的三项核心创新（活图谱、边级可靠性与生命周期、锚定性控制边界）连同跨 App 泛化能力，分别由四个研究问题（RQ1–RQ4）承载，并通过基线对照与消融开关矩阵逐项验证。设计文档中给出的延迟与调用次数数字（如快速路径 ~0.5s、VLM 路径 ~5s、不同成熟阶段的端到端延迟）均为实测估算，仅用于陈述预期趋势，其有效性有待本章实验验证；本章全部量化结果以【实验数据待补充】占位。

### 4.1 研究问题

**RQ1（活性）**：在线学习与自动持久化机制相比静态冻结图谱，对任务成功率与跨任务效率的贡献有多大？具体包括两个子问题：(a) 随成功任务数增长，图谱覆盖率与快速路径命中率的演化曲线；(b) 在注入 UI 漂移（人为使若干 promoted 边失效）后，自修复闭环（统计偏移→降级→VLM 重探索→重新提升）恢复到漂移前性能所需的任务数。设计文档给出的"通常 3–5 次任务内恢复"为经验估计，有待验证。为使"在线更新"这一变量可被干净分离（基线②同时改变了更新策略与调度策略），消融矩阵（4.5 节）另设"AMSG 调度协议不变 + 图谱冻结"的单变量对照：关闭成功任务落库与生命周期统计更新，其余机制保持完整。RQ1(b) 的漂移注入协议为：随机选取 k 条 promoted 边，篡改其 `target_locator` 坐标与 `postcondition` 以模拟按钮移位与流程变更；该模拟与真实 UI 漂移（应用版本更新）之间的差距将在结果分析中讨论。

**RQ2（可靠性度量）**：边级成功率追踪与四阶段生命周期（hypothesis→candidate→promoted→demoted）相比布尔存在性边，对错误快速路径执行率与规划质量的影响如何？布尔边将多结果转移（登录拦截、A/B 弹窗）一律视为有效转移，预期会产生不可靠的快速路径与误导性规划；生命周期机制以 t+1 延迟后条件验证为统计根基，仅放行统计达标的边。

**RQ3（控制边界）**：锚定性逐边调度相比两个极端——全 RAG（PG-Agent 式：图谱仅做提示注入，VLM 每步推理）[PG-Agent, ACM MM 2025] 与全 Teleport（WebNavigator 式：图谱内全部边一律直接重放）[WebNavigator, arXiv 2026]——在"成功率—端到端延迟—VLM 调用次数"三维权衡空间中处于什么位置？我们预期逐边调度能同时逼近全 RAG 的成功率与全 Teleport 的延迟，但该预期来自设计文档的实测估算趋势，有待验证。

**RQ4（泛化与冷启动）**：五阶段建图管线、同域结构先验与开放词表对陌生 App 冷启动各贡献多少？以京东（含秒送外卖链路）作为"陌生 App"场景，度量从零图谱到核心流程覆盖所需的探索轮次与人工审核成本。本文仅以京东这一个 App 作为冷启动对象，且其与淘宝同为头部电商、界面范式相近；因此 RQ4 的结论定位为**管线在同域新 App 上可复制性的案例研究**，而非一般性的跨 App 泛化结论——同域结构先验的效果在单一目标 App 上无法与 App 特异性因素完全区分，扩展到界面范式差异更大的购物域 App 列为后续工作（另见第 5 章局限）。

### 4.2 实验环境

评测采用真机 Android 在线评测而非离线步级匹配。如第 2.4 节所评述，AitW 类离线基准 [AitW, NeurIPS 2023] 以预录轨迹的动作匹配为指标，无法度量闭环任务成功率，也无法体现弹窗、广告、A/B 测试等真实干扰下的导航鲁棒性，而后者正是 AMSG 针对的问题域。

目标 App 为两个真实中文电商应用：淘宝（核心购物流程）与京东（核心流程及秒送外卖链路）。执行模型为 autoglm-phone-9b 类小型 GUI 模型，负责全部逐步动作生成；强 VLM 经三级 provider 链配置，与页面分类器、里程碑监督者、轨迹审核器及探索规划器共用同一链路。需如实说明强 VLM 在线介入的两个渠道：其一，每步感知阶段的页面分类器经该链路调用强 VLM（RuntimeDAG 命中时跳过该次调用），即在线逐步执行中的页面分类本身会消耗强 VLM 调用——强 VLM 不参与的仅是逐步动作生成；其二，里程碑监督机制（默认开启，预算约每任务 1 + 步数/5 次调用）在任务拆解与里程碑处低频介入。除非另行说明，本文全部实验保持里程碑监督的默认开启状态，并固定图谱生命周期预设为 `sava`（3.4.3）。任务集为中文电商长程任务，覆盖多条件筛选、价格区间约束与规格选择三类约束组合，完整任务清单与难度分布见附录【实验数据待补充】。实验环境配置（设备型号、系统版本、Neo4j 版本、网络条件）见表 7【实验数据待补充】。

### 4.3 基线

我们对比四个系统：① **纯 VLM 无图谱**：每步完整 VLM 推理，无任何图谱辅助，代表无记忆的下界；② **静态图谱 + RAG**（PG-Agent 式协议）：图谱冻结、在线只读，图谱知识仅作为提示注入，VLM 仍每步推理；③ **静态图谱 + 直接重放**（WebNavigator/Teleport 式协议）：图谱内全部边（不区分生命周期阶段）一律直接重放，无降级回退；④ **AMSG 完整系统**。

静态基线②③的图谱构建协议须显式说明：二者使用 AMSG 在完成第 K 个任务后的图谱快照并冻结（基线③将快照中全部边视为可重放，基线②仅将快照作为检索源），以保证三个含图谱系统的初始建图质量一致、差异归因于控制协议而非图谱内容；K 的取值理由与对快照时点的敏感性分析见【实验数据待补充】。需要注明，基线②③并非原系统的直接运行，而是在本框架内对其控制协议的复刻实现（re-implementation）：复用相同的感知、动作执行与图谱存储基础设施，仅替换图谱的更新策略与调度策略。各基线在统一任务集上的对比结果同样汇总于表 6【实验数据待补充】。

### 4.4 评价指标

指标分四组。**任务级**：任务成功率、平均步数、端到端延迟、每任务 VLM 调用次数——后者分别统计执行模型调用与强 VLM 调用，强 VLM 调用计入页面分类器与里程碑监督调用（见 4.2 节），因此 RQ3 的"快速路径节省调用"同时体现为跳过执行模型推理与 RuntimeDAG 命中时跳过分类器调用两部分。**图谱级**：快速路径命中率（快速路径执行步数占比）、promoted 边精确率（即错误快速路径执行率的补，度量生命周期门控质量）、图谱覆盖率增长曲线（覆盖的页面类型与转移占域模式覆盖目标的比例，随任务数演化）。**鲁棒性**：UI 漂移注入后恢复所需任务数（对应 RQ1b）。**建图成本**：五阶段管线的人工审核漏斗通过率（探索候选→审核批准→在线提升各环节的转化率，对应 RQ4）。各指标定义与测量方法的形式化描述及结果见表 8【实验数据待补充】。

## 5 结论与局限

本文针对小型 GUI 模型在高干扰真实移动应用中的长任务迷失问题，提出了主动移动空间图谱（AMSG），将页面-动作图谱从静态的导航知识库升格为随执行持续生长、自我修正的自进化动作库。本文的贡献与第 1 章所列逐项对应。其一，以在线学习与自修复降级机制构成"活的图谱"——每次成功任务经规范化与双重质量门后自动写回 Neo4j，UI 漂移引起的统计偏移自动触发边降级与重新探索，无需人工检测，区别于 PG-Agent 等方法建完即冻结的静态图谱 [PG-Agent, ACM MM 2025]；其二，以边级成功率追踪与 hypothesis→candidate→promoted→demoted 四阶段生命周期取代布尔存在性建模，并以 t+1 延迟后条件验证作为全部统计量的真实性根基——成功率来自"实际到达哪"而非"以为会到哪"；其三，以锚定性分类为每条边独立划定图谱与 VLM 的控制边界，锚定且统计可靠的边走快速路径以节省 VLM 调用，非锚定边永远保留 VLM 推理，避免了"始终 RAG"与"直接 Teleport"两个极端；其四，给出了可复制的陌生 App 五阶段冷启动建图管线（强 VLM 规划与小型 GUI 模型执行分离、staging 规范化、人工审核门、hypothesis 入图），并以多 App 单库逻辑分区与同域结构先验支撑跨 App 泛化。系统已在淘宝与京东两个真实 App 上完成核心购物链路（含京东秒送即时零售链路）的功能性端到端运行验证（冷启动建图入库与核心任务跑通）；系统性量化评测尚在进行，框架与结果占位见第 4 章【实验数据待补充】。

本工作仍存在若干技术性局限。第一，领域模式目前仅在购物域（shopping.yaml）得到充分实例化，扩展到外卖、出行等新领域仍需一次性的模式工程（页面类型词表、风险等级、典型转移的人工定义）；开放词表机制能让词表随观测进化，但只能缓解而非消除这一前置成本。第二，冷启动建图管线并非全自动：staging 批次须经人工审核门方可入图，验证码与登录墙依赖人工接力处置，建图的人工成本尚未量化，这限制了管线向大规模 App 集合扩展时的吞吐；此外，管线可复制性与同域结构先验的证据目前仅来自京东这一个同域 App（样本量为 1），且其与淘宝同为头部电商、界面范式相近，跨 App 泛化的结论因而受样本限制，应解读为案例研究证据。第三，当前图谱规模较小（不足 50 个节点，内部观察）：Belief-A* 规划因在此规模下增益小于 0.1 而默认关闭，多通道信念定位因现有 `(app, page_type)` 匹配已覆盖绝大多数场景而默认关闭，熵驱动验证边界则由域模式的静态配置替代；大规模图谱下的定位歧义、规划开销与检索行为尚未得到验证。第四，文中报告的延迟与 VLM 调用次数（如快速路径 ~0.5s、VLM 路径 ~5s）均为实测估算而非受控测量，系统性的量化评测——包括与 PG-Agent 等图谱基线在统一环境下的受控对比与消融实验——是下一步工作的核心。在此基础上，我们计划将生命周期统计扩展为熵驱动的 VLM 验证边界、探索跨域结构迁移，并研究图谱导航与里程碑级监督机制的协同（后者属另文主题，此处不展开）。
