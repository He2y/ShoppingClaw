# 3 方法

本章系统阐述 AMSG 的设计。3.1 节给出问题的形式化设定与总体架构，并说明三项核心设计决策与第 1 章所述三个缺陷的一一对应关系；3.2 节定义图谱的表示层——语义页面状态、语义动作节点、领域模式与多 App 组织；3.3 节阐述运行时集成，即锚定性边界划分与图谱如何赋予 Agent 空间感知；3.4 节给出在线学习机制、边生命周期与自进化闭环；3.5 节描述面向陌生 App 的五阶段建图管线。贯穿全章的有两条设计不变量：其一，**没有任何原始动作被直接写入 Neo4j**——一切观测在进入正式图谱前必须通过相应的质量门（在线路径见 3.4，离线路径见 3.5）；其二，**人工批准不豁免在线验证**——即便经人工审核入图的边，也仅以 hypothesis 阶段存在，对 Agent 不可见，直至其在线执行统计达标。这两条不变量共同保证：图谱中每一条对 Agent 可见的边，其可靠性都建立在经过验证的真实执行统计之上，而非建图者（无论是模型还是人）的单方面断言。

## 3.1 总体设计

**问题设定。**我们将一个移动 App 的可达状态空间建模为页面—动作二部图。在 Neo4j 中，其基本模式为：

```
(UIState) -[NEXT_ACTION]-> (Action) -[PRODUCES]-> (UIState)
```

其中 UIState 节点表示一个语义抽象的页面状态（定义见 3.2），Action 节点表示一个语义层面的可执行操作，NEXT_ACTION 关系表示"该页面上存在此操作"，PRODUCES 关系表示"该操作产生此目标页面"。在此模型下，一次任务执行对应图上的一条路径：从入口页面节点出发，经一系列 (Action, PRODUCES) 转移到达任务目标页面。Agent 的每步执行循环可抽象为五个阶段：**截图**（感知当前屏幕并分类页面类型）→ **定位**（将当前观测匹配到图谱节点）→ **调度**（依据图谱上下文决定本步由快速路径还是 VLM 推理产生动作）→ **执行**（在设备上施加动作）→ **验证**（在下一步开头核对实际到达页面与预期后条件，即 t+1 延迟验证，详见 3.4）。任务执行因而成为"在图上行走、同时为图累积统计证据"的过程——这正是 AMSG 区别于只读图谱方法的结构性前提。

**三项设计决策。**针对第 1 章归纳的现有图谱方法三个根本缺陷，AMSG 作出三项一一对应的设计决策。其一，针对**静态冻结**缺陷，采用**自动持久化的活图谱**：图谱不是离线一次性构建的产物，而是随每次成功任务自动生长、随可靠性统计下降自动收缩的在线结构（机制见 3.4）；离线建图管线（3.5）仅解决冷启动，不构成图谱的最终形态。其二，针对**边的布尔存在性**缺陷，采用**边级成功率追踪与四阶段生命周期**：每条边携带真实执行统计，并在 hypothesis → candidate → promoted → demoted 的状态机中流转，只有统计上可靠的边才对 Agent 可见（3.4）。其三，针对**图谱/VLM 边界一刀切**缺陷（要么如 PG-Agent [PG-Agent, ACM MM 2025] 永远 RAG 不省调用，要么如 WebNavigator [WebNavigator] 永远 Teleport 无回退），采用**锚定性分类**：每条边独立标注其转移是否可由图谱机械完成，逐边决定控制强度（3.3）。

**总体架构。**图 1 给出 AMSG 的总体架构（占位：可基于 `phone_agent/docs/图谱设计.png` 素材重绘）。系统在逻辑上分为三层。**表示层**定义图谱存什么：语义页面状态及其去重签名、语义动作节点、作为结构先验的领域模式、多 App 单库逻辑分区（3.2）。**运行时层**定义图谱如何被消费：统一定位入口、Dijkstra 路径规划与 RuntimeDAG 缓存、锚定性驱动的调度边界（3.3）。**学习层**定义图谱如何演化：质量门控的自动持久化、t+1 延迟后条件验证、边生命周期与自修复（3.4）。值得强调的是供给与消费的结构关系：离线建图管线（3.5）与在线学习（3.4）是图谱的**两条独立供给线**，各有独立的质量门；但二者产出的边汇入**同一套生命周期消费线**——无论来源是探索审核还是任务执行，新边一律以 hypothesis 入图，经统一的在线验证统计才能晋升为 Agent 可见、可执行的知识。这一"双供给、单消费"结构是前述两条不变量的架构化体现。

## 3.2 图谱表示

### 3.2.1 语义页面状态与去重签名

UIState 节点不存储截图或截图哈希，而存储一个语义元组：

```
PageState = (app, page_type, landmarks, affordances, slots, risk_level)
```

其中 `app` 为应用标识，`page_type` 为页面类型（如 `search_result`、`product_detail`），`landmarks` 为页面地标元素集合，`affordances` 为可操作项集合，`slots` 为页面携带的任务槽位，`risk_level` 为风险等级标注。放弃截图哈希的理由是复用性：在购物 App 中搜索"iPhone"与搜索"耳机"，两次截图在像素层面完全不同，但页面结构相同（搜索栏 + 商品列表 + 筛选按钮）。若以截图哈希去重，每次搜索不同关键词都会产生新节点，图谱持续膨胀却无法复用任何导航知识；而以 `(app, page_type)` 级别的语义抽象建模，同一个 `search_result` 节点即可在所有购物任务中复用。去重依靠确定性语义签名 `app|domain|page_type|landmarks|affordances|slots`（`spatial/core.py:semantic_signature()`）：签名相同的观测被合并到同一节点。签名的确定性（同输入必同输出，不依赖任何模型推理）保证了去重行为的可复现性。

### 3.2.2 语义动作节点

Action 节点同样以语义而非坐标为身份：

```
Action = (type, intent, semantic_target, postcondition, lifecycle_stage)
```

其中 `type` 为动作类型（Tap、Type 等），`intent` 为语义意图（如 `open_search`），`semantic_target` 为目标元素的语义描述，`postcondition` 为预期到达的页面类型，`lifecycle_stage` 为该动作所处的生命周期阶段。坐标不参与节点身份："点击搜索按钮"在不同分辨率、不同设备上的坐标各不相同，但语义完全一致——若以坐标为身份，同一意图会在跨设备场景下裂解为多个节点。坐标仅作为 `target_locator` 属性附加在动作上，充当锚定证据（其在快速路径中的使用见 3.3）。动作去重键为 `source_page_type|intent|semantic_target|region|target_page_type`（`memory/graph_store.py:_semantic_action_key()`），确保坐标不同但意图相同的观测合并为同一动作。在关系层面，每条边记录执行统计：`frequency`（成功次数）、`fail_count`（失败次数）与 `confidence`（成功次数占总次数之比）。本节只界定这些统计**存什么**；它们如何被 t+1 延迟验证更新、如何驱动生命周期流转，留待 3.4 阐述。

### 3.2.3 领域模式：结构先验与开放词表

图谱不是无约束生长的。领域模式（domain schema，`spatial/schemas/shopping.yaml`）为购物场景定义了结构先验：页面类型词表及各类型的风险等级与典型地标、典型转移集合、探索覆盖目标、危险动作词表（按 common → 域 → App 三级累加）、干扰页面集合（dialog/permission/login/ad/captcha）、陷阱词表，以及默认探索任务模板（以 `{app}` 占位，一份任务文本服务整个领域）。模式的职能是**规范化**（如将分类器输出的 "detail" 归一为 `product_detail`）与**风险标注**（如 `checkout` 始终标为高风险），而非限制图谱生长——图谱可以学到模式未预定义的转移，只要其通过质量门。页面分类器的系统提示词完全由模式生成（`memory/exploration/classifier_prompts.py:build_fast_prompt`），因此模式扩展可直接改变分类行为而无需修改代码。

封闭词表是跨 App 泛化的瓶颈：真机测试中，外卖商家页曾被分类器硬塞为词表内最接近的 `product_detail`，造成系统性的页面误判。这一案例催生了**开放词表**机制：分类器遇到词表外的页面时，输出 `new:<类型名>` 加一句话定义，进入提案池；提案出现不少于 2 次才浮出供审阅，且**永不直接建边**，须经人工审核后合入域模式或 App profile。该机制在后续扩展中得到定性验证：为 shopping.yaml 增加即时零售类型（`channel_home` 频道首页、`shop_list` 商家列表及 `store` 的覆盖扩展）后，京东秒送的外卖链路无需修改任何代码即被正确分类。模式因而成为一个"有先验、可进化"的词表：先验保证图谱噪声可控，开放词表保证领域边界可随真实 App 形态扩张。

### 3.2.4 多 App 组织：单库逻辑分区

多个 App 的图谱不拆分为多个 Neo4j 库,而在单库内按 `app` 属性逻辑分区。三个理由：其一，跨 App 结构迁移的聚合查询（泛化能力的核心支撑，见 3.3 的同域结构先验）在单库内是一条 Cypher 语句，多库方案则需 Neo4j Enterprise Fabric；其二，节点本就携带 `app` 属性，查询天然按 App 作用域收敛；其三，单驱动连接池，无需维护 App 到库的路由层。App 身份由 AppRegistry 统一管理（`spatial/app_registry.py`，配置于 `schemas/app_registry.yaml`）：包名、中英文名与历史编码变体均映射到规范 `app_id`，再映射到所属 `domain`。每个节点写入三个字段——`app`（规范 id，如 `jd`，所有程序检索的作用域键）、`app_raw`（注册表主显示名，如"京东"，供人工浏览过滤）、`domain`（领域，如 `shopping`，跨 App 聚合的分区键）——并建立复合索引 `(app, page_type)` 与 `(domain, page_type)`，保证 App 内定位与跨 App 聚合两类查询均为索引命中（`GraphStore.ensure_indexes()`）。一条来自实践的设计经验：staging 节点与库内已有节点做规范合并后，同一条边的两端可能一端持规范 id（`jd`）、一端持原始值（`京东`），任何以精确相等比较 App 的代码都会静默丢边——因此系统中一切 App 一致性比较必须经由别名感知的 `_same_app()` 完成。
