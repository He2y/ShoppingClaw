# 3.3 运行时集成：锚定性边界与空间感知

上一小节定义了图谱的静态表示。本节阐述图谱如何在运行期发挥作用：AMSG 不是一个独立于执行器的离线知识库，而是通过 `GraphRuntimeController` 嵌入 Agent 每步执行循环的在线组件。本节首先提出本文的第三个核心创新——锚定性（groundedness）分类，它在每条边的粒度上划定图谱与 VLM 的控制边界（§3.3.1）；随后介绍承载这一边界的运行时机制：统一定位入口（§3.3.2）与路径缓存（§3.3.3）；接着论证支撑整个统计体系真实性的根基——t+1 延迟后条件验证（§3.3.4）；最后给出多 App 场景下的分层检索与上下文注入设计（§3.3.5）。

## 3.3.1 锚定性分类：在每条边上划定图谱与 VLM 的控制边界

现有图谱增强方法在"图谱与模型谁控制导航"这一问题上呈两个极端。[PG-Agent, ACM MM 2025] 与 [KG-RAG, EMNLP 2025] 将图谱仅作为 RAG 检索源，VLM 在每一步仍需完整推理——图谱改善了提示内容，却不减少任何一次模型调用；[WebNavigator, arXiv 2026] 则让图谱直接执行 Retrieve-Reason-Teleport 式跳转，隐含"图谱总是正确"的假设，边失效时没有回退机制。两个极端共享同一个盲点：它们不区分"图谱可独立完成的转移"与"必须观察屏幕内容才能决定的转移"。

AMSG 的回答是在**每条边**上标注锚定性：一条边是锚定的（grounded），当且仅当其对应的转移可以由图谱独立执行、无需感知当前屏幕的具体内容；否则为非锚定（ungrounded），必须由 VLM 观察截图后选择具体目标。表 1 以购物域的四条典型转移说明这一区分：

**表 1：锚定性分类示例（购物域）**

| 转移 | 锚定？ | 原因 |
|---|---|---|
| `home → search_input` | 是 | 搜索按钮位置固定 |
| `search_input → search_result` | 是 | 输入 + 提交，机械操作 |
| `search_result → product_detail` | **否** | 选哪个商品取决于当前任务 |
| `product_detail → spec_selection` | **否** | 选什么规格取决于用户需求 |

这一区分的本质洞察是：移动 App 的页面转移天然分为两类——位置固定的**机械转移**（点击搜索框、提交查询、启动应用）与依赖屏幕内容的**决策转移**（在搜索结果中挑选商品、在规格弹窗中选择型号）。前者的正确执行只需要历史上验证过的坐标与操作序列，后者的正确执行原则上无法脱离当前截图与任务语义。把两类转移交给同一种控制方式，要么浪费（对机械转移做完整 VLM 推理），要么危险（对决策转移做盲目重放）。

在实现上，系统以 `_UNGROUNDED_TRANSITIONS` 清单（共 9 对页面类型转移）强制划定永不可快速执行的边界，涵盖三类情形：内容决策类（`search_result→product_detail` 选哪个商品、`search_result→store` 选哪家店、`product_detail→spec_selection` 选什么规格、`filter_panel→search_result` 离开筛选需内容决策、`spec_selection→product_detail` 弹窗关闭/取消决策）；购买提交类（`spec_selection→cart`、`spec_selection→checkout`、`cart→checkout`——高风险提交点即使边统计上可靠也永不自动执行）；以及机械陷阱类（`search_input→search_result` 的裸 Tap 会提交输入框中的残留文本，必须经复合动作合成后才可锚定，见下）。此外，**Back/Home 等撤销类动作永不进入快速路径**：撤销属于修复域，图谱无法区分"Agent 偏离了路线"与"模型有意绕路"（例如绕开弹窗），自动重放撤销动作会与模型的合理决策相对抗。

锚定性标注存在一个与在线学习交互的细节：`search_input→search_result` 在文档语义上是"输入 + 提交"的复合机械动作，但在线轨迹只会记录到一次裸 Tap。为此 `ActionAdvisor._append_search_compound` 从已验证的 Tap 坐标**合成**一条 grounded 的 Compound 提示——`Type <query>` + `Tap 坐标`，其中 `<query>` 槽位在执行时由当前任务计划填充。这一合成使搜索这一最高频的机械步骤真正能走快速路径，而不是因轨迹记录粒度的限制被迫退回 VLM。

锚定性与边生命周期状态（§3.4）共同决定三档调度：

1. **快速路径（Fast Path）**：锚定且 promoted 的边直接由图谱执行，跳过 VLM，单步约 0.5 秒（实测估算）；
2. **Graph Co-pilot**：标注为 `verify_with_vlm` 的转移由图谱给出方向性提示（语义目标、路径概要），VLM 负责在截图上完成具体 grounding；
3. **完整 VLM 推理**：非锚定边或图谱无路由时的默认路径，单步约 5 秒（实测估算）。

快速路径的准入判据由 `ActionAdvisor.is_fast_executable()` 实现：`grounded=True` 且 `confidence ≥ 0.9` 且（有已验证坐标，或为合成 Compound，或动作类型属于 {Launch, Wait}）。其中置信度阈值 0.9 是设计参数而非调优结果。与前述两个极端对比，AMSG 的控制边界不是系统级的一刀切，而是**每条边独立决定控制强度**：图谱在它确定可靠的机械转移上完全接管以节省模型调用，在依赖内容的决策转移上退为提示者，把 grounding 权威留给 VLM。

## 3.3.2 统一定位入口：locate_and_get_context()

图谱知识进入执行循环的唯一入口是 Agent 循环 Phase 3 调用的 `locate_and_get_context()`（由 `MemoryManager` 委托给 `GraphRuntimeController`）。该方法在一次调用中完成六步：① 页面匹配——以 `(app, page_type)` 复合键查询 Neo4j 定位当前页面节点；② 验证上一步缓存的 pending transition（见 §3.3.4）；③ 目标推断——从任务槽位（TaskSlots）推导目标规格（GoalSpec，目标 page_type 与槽位约束）；④ Dijkstra 加权最短路规划从当前节点到目标的路径；⑤ 将规划结果缓存为 RuntimeDAG（见 §3.3.3）；⑥ 返回调度模式 `mode` 及候选动作与语义上下文。

返回的 `mode` 直接驱动后续调度决策：

**表 2：locate_and_get_context() 的四种返回模式**

| mode | 含义 | Agent 行为 |
|---|---|---|
| `navigate` | 图谱有路径，下一步可执行 | 锚定边 → 快速路径；非锚定边 → VLM + 提示 |
| `explore` | 图谱无路径（冷启动或覆盖缺口） | 完整 VLM 推理，图谱记录新观测 |
| `verify_with_vlm` | 图谱有方向但需 VLM 选择具体元素 | VLM 推理 + 图谱语义目标提示 |
| `goal_reached` | 当前页面已是目标 page_type | 无需导航动作 |

这一设计把"定位、验证、规划、缓存"压缩为每步一次的原子调用，使图谱对执行循环的侵入面保持最小：Agent 主循环只消费一个 `mode` 字段与一组提示，无需理解图谱内部状态。

## 3.3.3 RuntimeDAG：路径缓存与按需失效

Dijkstra 规划本身在微秒量级完成，但完整定位管线（Neo4j 查询 + 规划 + 上下文组装）每步需 50–200 毫秒（工程量级估算）。考虑到多步导航中相邻步骤通常沿同一条规划路径推进，逐步重复完整管线是纯粹的浪费。RuntimeDAG 将一次规划的结果缓存为内存中的边数组与游标：缓存命中时直接取 `route[current_index]` 返回下一动作，耗时约 10 毫秒（实测估算），不再查询 Neo4j。

缓存的正确性由四项失效条件保证：后条件不匹配（实际到达页面与路径预期不符）、应用切换、连续失败超过阈值、下一步为高风险边。任一条件触发后 DAG 作废，下一步 Phase 3 自动重建完整管线。失效是被动且廉价的——系统不试图增量修补过期路径，而是直接重新规划。

RuntimeDAG 带来一个值得明确陈述的副作用与代价权衡：DAG 可用时 `should_use_page_classifier()` 返回 False，Phase 1 跳过 PageClassifier 的 VLM 调用，进一步节省一次模型调用；其代价是当弹窗等意外页面出现时，Agent 会带着错误的 page_type 多走一步。这个错误不会累积——下一步的延迟后条件验证（§3.3.4）会发现实际页面与预期不符，记录失败观测并触发 DAG 失效与重建。换言之，系统有意接受"单步延迟发现"以换取稳态下的调用节省，并以验证机制兜底。

## 3.3.4 t+1 延迟后条件验证：统计真实性的根基

锚定性调度与下一节的边生命周期都建立在边级成功率统计之上，而成功率统计的价值完全取决于其数据来源是否真实。AMSG 以**延迟后条件验证**回答这一问题：Agent 循环的 Phase 6 在执行动作后，将三元组（当前页面，动作，预期目标页面）暂存为 pending transition；下一步（t+1）Phase 3 的开头，将 PageClassifier 对新截图给出的实际 page_type 与预期目标对比——匹配则记 `record_observation(outcome="success")`，不匹配则记 failure 并触发修复策略（DAG 失效、回退 VLM 路径等）。

这一机制的必要性可以从反面论证：若没有后条件验证，边成功率的统计来源是"Agent 以为这个动作会到达哪个页面"，而非"动作执行后实际到达了哪个页面"。在高干扰的真实 App 环境中，二者系统性地不一致——登录拦截、A/B 实验弹窗、促销浮层都会让同一动作产生预期之外的结果。建立在"以为"之上的成功率是自我报告，建立在"实际"之上的成功率才是经验事实。整个边生命周期系统（hypothesis 的提升、promoted 边的降级、自修复）的正确性都以这一事实流为前提。据我们所知，[PG-Agent, ACM MM 2025]、[KG-RAG, EMNLP 2025]、[WebNavigator, arXiv 2026] 均不具备后条件验证机制：它们的图谱中"边存在"这一事实从建图时刻起便不再接受经验检验。

验证机制本身还需要防御一种隐蔽的退化。一个看似合理的"优化"是把运行时的预期后条件喂给 PageClassifier 作为分类偏置——既然图谱预期下一页是 `search_result`，让分类器倾向这一答案似乎能提高分类稳定性。AMSG 将其确立为一条架构红线并**有意识地拒绝**：分类器的输出是后条件验证的 ground truth，一旦验证的裁判被验证的预期所偏置，验证就退化为自我证实——预期什么便"看到"什么，失败的边永远不会被记为失败，生命周期统计的真实性随之坍塌。保持分类器对运行时预期的独立性，是统计体系可信的结构性前提，其地位等同于实验科学中测量仪器对假设的独立性。

值得说明的是，快速路径执行还配有一道**同步**后条件检查：`_execute_fast_path` 在执行后立即截取新屏并分类，失配时当步回退模型路径并记失败观测，最坏代价是多一次模型调用。同步检查保护单步执行的即时正确性，t+1 延迟验证则覆盖包括模型路径在内的全部转移并供给统计流，二者互补。

## 3.3.5 多 App 分层检索与同域结构先验

当图谱服务于多个 App 时（§3.2 的单库逻辑分区），运行时检索按三层组织，且**只有第一层产生可执行动作**：

1. **App 专属子图**：前台 App 检测经 AppRegistry 规范化后，所有查询以规范 App id 为作用域。promoted 边的快速路径**只能**来自这一层——可执行的坐标永远属于当前 App 自己验证过的边。
2. **同域结构先验**：当 App 子图过冷（节点覆盖低于阈值）且 `mode=explore` 时，注入同域其他 App 在当前页面类型上的常见转移——由领域模式中的 schema 转移与跨 App promoted 边聚合而成，按支持度排序。关键约束是这一层**仅作为文本提示进入语义上下文，绝不携带坐标**：其他 App 的 `target_locator` 禁止执行，从机制上杜绝跨 App 坐标污染。其效果可概括为"京东冷启动时借用淘宝沉淀的购物结构方向感"——新 App 没有可执行的边，但获得了"购物 App 的搜索结果页通常可进入筛选面板与商品详情"这类结构性方向感。该层可由 `AMSG_DOMAIN_PRIORS=0` 关闭以作消融。
3. **common_mobile 兜底**：dialog/permission/login/captcha 等通用干扰页的处置知识，与具体域无关。

图谱知识最终经两条通道进入 VLM 提示：**导航上下文**在 `mode=navigate` 时注入"当前位置 → 目标"的路径概要与下一步动作描述，VLM 可采纳亦可忽略——图谱在此是建议者而非指挥者；**动作提示**由 `ActionAdvisor.query()` 给出当前页面全部 promoted 边的列表，其中非锚定边只提供"该转移存在"的信息而不提供坐标，VLM 必须自行观察截图决定具体目标。两条通道与 §3.3.1 的控制边界一致：坐标级的执行权严格限定在锚定且可靠的边上，其余一切图谱知识都以可拒绝的文本提示形式存在。

综上，运行时集成层以锚定性划界、以统一入口接入、以路径缓存提效、以延迟后条件验证守真。每一步执行结束时，后条件验证产生的成功/失败观测流即是图谱保持"活性"的数据来源——这一事实流如何被消费、如何驱动边的提升与降级乃至图谱的自修复，是下一节在线学习与边生命周期机制的主题。
