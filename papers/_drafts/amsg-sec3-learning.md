# 3.4 在线学习、边生命周期与自进化

前两节解决了图谱"长什么样"（3.2）与"怎么用"（3.3）的问题；本节回答图谱"如何生长"——这是 AMSG 名称中"主动"（Active）一词的实质所在，也对应本文第一、二项核心创新。3.3 节的 t+1 延迟后条件验证为每条边持续产生基于真实观测的 success/failure 计数，本节阐述这一事实数据流如何经由双重质量门、四阶段生命周期与自动降级机制，将一个静态的导航知识库转变为持续自进化、可自修复的活图谱。

## 3.4.1 自动持久化管线与质量门 1：任务级成败过滤

AMSG 的持久化管线遵循一条贯穿全系统的核心规则：**没有任何原始动作观测直接写入 Neo4j**。任务执行期间，每步产生的页面状态与转移观测全部暂存于内存结构 `_local_states` 与 `_local_edges` 中，同时 `EdgeLifecycleManager.record_outcome()` 在内存中更新对应边的成功/失败计数与优势比。按定义，一个 20 步的任务约产生 20 个暂存观测；整个过程不触碰持久化存储。

只有当任务以成功状态结束、即 `end_task(success=True)` 被调用时，系统才触发 `flush_staged_graph()` 将暂存观测落库；失败任务的全部暂存观测被整条丢弃。这构成第一道质量门，其设计论点是：失败轨迹的观测可能整条都是错误导航——走错路径、陷入循环、被弹窗劫持——写入图谱会系统性污染后续任务的规划。正如源设计文档所述："一个 20 步的失败任务可能有 15 步是错误操作，直接丢弃比逐步审核更高效。"任务级的粗粒度过滤以可忽略的召回损失换取了零审核成本的高精度，这与逐步细粒度审核相比是一个有意为之的工程取舍：错误观测的代价（污染规划、误导后续所有任务）远高于丢弃少量正确观测的代价（下次成功任务仍会再次观测到）。

`flush_staged_graph()` 的落库过程分三步。第一步，`canonicalize_state_graph()` 执行规范化与过滤：按语义签名（3.2 节）对页面状态去重，使"搜索 iPhone"与"搜索耳机"得到的结构相同的结果页合并为同一节点；过滤 `unknown` 类瞬态页面；执行应用一致性检查，拒绝跨应用页面间的非法直接转移边。第二步，对每条暂存边执行生命周期提升检查（条件见 3.4.3）。第三步，以 Cypher `MERGE` 语义将页面状态与转移写入 Neo4j——`MERGE` 保证幂等性，重复写入不产生重复节点；边的生命周期元数据（`lifecycle_stage`、`verification_count`、`dominance_ratio`）作为 Action 节点属性同步落库，使生命周期状态跨会话持久。

## 3.4.2 质量门 2：VLM 轨迹审核

第一道门过滤的是"整条任务级"的噪声，但成功任务内部仍可能混入页面分类器误判产生的虚假转移——典型案例是 `dialog → home`：Agent 关闭一个广告弹窗回到首页，被分类器误读为"存在一条从对话框页通向首页的导航边"，这类边一旦入图会误导路径规划。为此，`flush_staged_graph()` 完成后，`TrajectoryReviewer.review_and_import()` 对保存的轨迹 JSON 执行第二道审核：① 提取步骤间的页面转移链；② 过滤同页、`unknown`、`finish`、`wait` 等伪转移；③ 与 Neo4j 现有边比对去重，已知转移不重复处理；④ 将新转移候选提交给强 VLM（由 `AMSG_STRONG_VLM_MODEL` 配置，独立于执行用的小 GUI 模型）判定真伪。审核提示词的核心片段如下：

> 你是一个手机 App 页面导航图谱的质量审核员。以下是从执行轨迹中提取的新页面转换。请判断每条转换是否是真实有效的页面导航。
> 有效：从一个明确的页面类型跳转到另一个明确的页面类型。
> 无效：dialog → home（关闭广告弹窗），分类器错误导致的虚假转换。

仅获 VLM 批准的转移以 `lifecycle_stage="hypothesis"` 导入图谱——即便通过审核，它们对 Agent 仍不可见（3.4.3）。

该管线的迭代过程中沉淀了两条失败安全（fail-safe）设计经验，值得作为系统设计教训记录。其一，VLM 输出解析失败时，候选必须标记为"未审核"而非默认通过——早期实现采用"解析失败则全部通过"的反向回退，等价于在审核器最不可靠的时刻把质量门完全打开，是危险的失效模式。其二，导入必须以语义键 `MERGE` 而非 `CREATE` 执行——早期 `CREATE` 实现会在审核流程重跑时产生重复 Action 节点，破坏图谱的去重不变量。审核判定逻辑封装为共享组件 `VlmTransitionJudge`，同时服务于此处的在线审核与离线探索数据的批次审核；离线建图管线另设独立的人工审核质量门，见 3.5 节。

## 3.4.3 四阶段边生命周期

通过双重质量门入图只是边生命的起点。AMSG 用一个四阶段状态机管理每条边从"被观测到"至"可被执行"的全过程（如图 X 所示，边生命周期状态机，图号待全文统一）：

```
hypothesis → candidate → promoted → demoted
                              ↑__________|（重新验证达标后可再提升）
```

各阶段对 Agent 的可见性如表 X 所示：

| 阶段 | 语义 | 对 Agent 的可见性 |
|---|---|---|
| `hypothesis` | 已观测/已审核，但未经运行时验证 | 不可见，不能用于快速路径 |
| `candidate` | 验证次数达标但结果分布尚不稳定 | 不可见 |
| `promoted` | 统计可靠 | **可见**：锚定边进入快速路径，非锚定边作为 VLM 方向提示 |
| `demoted` | 曾经可靠但成功率坍塌 | 不可见，交还 VLM 重新探索 |

这张可见性表是生命周期设计的要害：**只有 `promoted` 边对运行时 Agent 可见**，且即使可见，其作用方式仍受 3.3 节锚定性边界约束——锚定边可绕过 VLM 直接执行，非锚定边只提供"该转移存在"的方向性提示。换言之，一条边要影响 Agent 的实际行为，必须同时跨过统计可靠性（生命周期）与控制权限（锚定性）两道独立的门。

提升条件为三项合取：`verification_count ≥ N` 且 `dominance_ratio ≥ θ` 且 `risk ≠ high`，其中 `verification_count` 为 3.3 节后条件验证累积的次数，`dominance_ratio` 为主导结果在全部观测结果中的占比——它比简单成功率更严格，因为同一动作通向多个不同结果页（登录拦截、A/B 弹窗）的边即使"次次有响应"也无法形成主导结果。N 与 θ 为系统设计参数（而非调优结果）：实现中默认预设取 N=1、θ=0.6，论文实验推荐的 `sava` 预设取 N=3、θ=0.8（`phone_agent/spatial/amsg_config.py`）。降级条件为：`promoted` 边的优势比跌破 0.4（设计参数）即自动降级为 `demoted`。

生命周期系统维持两条强不变量。**其一，人工批准不豁免在线验证**：经 3.5 节人工审核门批准入图的边同样以 `hypothesis` 起步，必须在真实执行中通过后条件验证累积到达标统计才能提升——人工判断回答的是"这条转移是否真实存在"，而只有运行时统计能回答"它是否可靠到值得绕过 VLM"。**其二，高风险目标边永不成为可执行快速路径**：如 `cart → checkout` 这类购买提交边，可以作为节点间连通性存在于图谱中以保证路径规划的结构完整性，但提升条件中的 `risk ≠ high` 子句使其永远停留在不可快速执行的状态——涉及资金与不可逆操作的转移，无论统计多么可靠，决策权永远保留给模型与上层安全护栏。

## 3.4.4 自修复：统计偏移作为 UI 漂移信号

静态图谱方法的根本困境在于：应用更新使边失效，而系统对此一无所知。AMSG 的生命周期机制使 UI 漂移的检测与恢复无需任何人工干预，其因果链如下：应用更新导致某条 `promoted` 边对应的按钮功能改变 → Agent 走快速路径执行该边 → t+1 后条件验证发现实际页面与预期不符，记录 failure，同时 Agent 回退 VLM 路径完成当前步 → 该边的 `dominance_ratio` 随失败累积而下降 → 跌破降级阈值后边被降级，Agent 不再使用 → 后续任务中 VLM 对该转移重新探索 → 新观测建立新的 `hypothesis` 边 → 经后条件验证达标后重新提升为 `promoted`。整个闭环中没有"UI 变更检测器"这样的专用组件——**成功率的统计偏移本身就是 UI 变更的信号**，检测与恢复完全由已有的验证-生命周期机制涌现。根据系统开发期的经验估计，该自修复过程通常在 3-5 次任务内完成（正式测量见第 4 章）。

## 3.4.5 自进化正反馈闭环与收敛性

以上机制组合形成跨任务的正反馈循环（可配闭环示意图，图号待统一）：成功任务经双质量门为图谱新增或强化转移 → 更多边累积验证统计并提升为 `promoted` → 后续任务中更多步骤命中快速路径 → VLM 调用减少、单任务延迟下降且确定性增强 → 任务更易成功 → 进一步喂养图谱。图谱由此从被动的"导航知识库"升格为随使用自动增值的"自进化动作库"。

一个自然的疑虑是该循环是否导致图谱无限膨胀。答案是否定的，其根据在于移动应用状态空间的有限性：一个典型购物 App 仅有约 8-12 种核心页面类型与 15-25 种常用转移（经验估计），且语义签名去重（3.4.1）保证同型页面不重复建节点。经验上，约 10-20 次成功任务后核心流程（首页 → 搜索 → 结果 → 详情 → 规格 → 购物车）的转移即基本覆盖，此后的成功任务以强化已有边的统计为主，仅偶尔发现边缘场景的新转移。就延迟而言，系统呈现出从冷启动期（无可用边，全程 VLM 推理）到稳定期（核心机械导航全部走快速路径）的单调改善趋势；值得指出的是，稳定期的延迟下界由非锚定步骤决定——选哪个商品、选什么规格这类依赖当前屏幕内容的决策步骤，无论图谱多么完善都必须保留给 VLM，这正是 3.3 节锚定性边界的设计本意。各阶段的量化延迟与快速路径命中率见第 4 章【实验数据待补充】。

在线学习解决了图谱的持续生长，但无法解决从零开始的冷启动——面对一个图谱从未见过的 App，不存在可供验证的边，也没有成功任务可供学习。下一节给出面向陌生 App 的五阶段建图管线。
