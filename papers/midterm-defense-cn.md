## 一、研究目标

各位老师好，我的课题面向移动端购物场景，研究**如何用一个能力有限、可量化部署到手机本地的小型 GUI 模型，在长程购物任务上达到接近云端大模型的可靠性**。

出发点是一个真实的"端云两难"：

- **云端大模型每步决策**：单步准，但前期真机实测表明，每步引入强 VLM 会使单步延迟增至约三倍，成本随步数线性增长、隐私差，且根本无法部署到手机端侧。
- **端侧小模型**：延迟、成本、隐私都友好，单步元素定位（grounding）也够用，但长程任务上暴露出系统性短板。我在淘宝、京东真机中反复观察到四类失败模式——**长任务焦点丢失、数字判断幻觉、伪完成、空响应**。例如模型曾连续三次把 ¥1424、¥172、¥201 三个明显越界的价格判成"在 500–1000 元内"，也曾在根本没执行加购时宣布"已加入购物车"。

这些不是偶发噪声，而是小模型能力上限与长程需求之间的结构性矛盾，**靠提示工程无法根除**——指望一个会幻觉的模型自己识别幻觉，逻辑上是循环论证。

因此我的核心命题不是"把决策权交还云端"，而是**用检索增强弥补小模型的能力短板**：小模型不依赖自身有限的参数化记忆做决策，而是在每个决策点从外部知识库检索相关知识来增强它——让高频执行留在端侧、确定性判断零云调用、语义监督只在关键点低频上云。

具体目标分解为三点：

a. 构建面向购物场景的**多源检索增强体系**，为小模型供给导航、偏好与长程事实知识；
b. 设计**低频语义监督与确定性护栏**，保障"检索—决策—执行"链路的可靠与安全；
c. 实现**多模型、多平台的工程系统**，并在真实电商应用上完成验证。

一句话概括我想验证的论断——**端侧小模型的长程可靠性，可以来自外部知识的检索增强与系统的确定性结构，而不是模型规模的扩张**。

为什么是检索增强？小模型的四类失败，根子都是"它脑子里没有、也记不住"该有的知识：不知道结果页该点哪里去筛选（缺导航知识）、不知道用户上次买的什么价位（缺偏好知识）、记不住几步前已经加过购（缺长程事实）。与其把这些硬塞进模型训练或每步问云端，不如把它们沉淀成**可检索的外部知识库**，需要时检索出来注入——这正是检索增强（RAG）的思路，也是本课题的技术主线。现有 GUI 智能体 RAG 方法（如 PG-Agent、KG-RAG）已验证了这一方向，但存在检索不省模型调用、知识库静态过期等缺陷，正是本文要改进的地方。

## 二、研究内容

围绕这个目标，我设计并实现了 Shopping-Agent。从检索增强的视角看，它的本质是**一个多源异构的检索层在为小模型供给知识**，按"检索什么知识"分为四类通道：

| 检索类型 | 检索引擎 | 检索什么 | 检索方式 |
|---|---|---|---|
| **图结构检索（导航知识）** | Neo4j / AMSG | 跨会话页面状态图谱：从哪到哪怎么走 | 复合索引定位 + Dijkstra 最短路 + 路径缓存 |
| **向量语义检索（偏好知识）** | FAISS | 用户历史品牌、价位偏好 | 嵌入向量近似最近邻召回 |
| **按需上下文检索（动态事实）** | 检索网关 | 候选商品、购物车计算、历史步骤 | 思考信号触发、按需注入、带冷却 |
| **记忆事实检索（抗遗忘）** | 会话记忆文件 | 已验证事实、子任务进度 | 每步结构化渲染注入 |

下面以三张核心图为主线介绍系统：**图 1 系统架构**给出整体的"三区域 + 监督层"与决策分工；**图 2 图谱设计**展开核心检索引擎 AMSG；**图 3 图谱构建管线**说明这套检索库如何为陌生 App 从零建起、又如何自我更新。

### 2.1 系统架构总览（图 1）

![系统架构总览](../phone_agent/docs/系统架构图.png)

**图 1 简要概述**：这张图自上而下分四层。最上是**监督层**（强 VLM，低频语义裁量），含里程碑监督器与会话记忆文件，只在任务开始 `initialize`、里程碑 `checkpoint`、完成 `final_confirm` 三个时机介入；中间是三个并列的逻辑区域——**决策区域**（PhoneAgent 编排器 + TaskPlan + 机械护栏 + SpecGuard + 三档调度）回答"做什么"，**图谱区域**（GraphRuntimeController + 定位 / Dijkstra / RuntimeDAG / ActionAdvisor / 边生命周期）回答"在哪、走哪"，**执行区域**（ModelClient + 协议桥 + 动作处理器 + 设备工厂）回答"怎么操作设备"；最下是**反馈与持久化闭环**——每步后条件验证回流更新成功率与边生命周期，任务成功才落库 Neo4j。

贯穿全图的设计原则是**非对称权威**：每类决策都交给最适合、且失败代价最小的主体——图谱只做机械导航不做语义判断，小模型保留对当前屏幕的 grounding 权威，机械护栏接管全部确定性判断（数字、证据、状态），强 VLM 只在关键点低频裁量。这张图也对应我的前两个创新点。

**创新点 1——强 VLM 里程碑监督 + 会话记忆文件**（图中监督层）。针对焦点丢失与伪完成这类语义层问题，我取"每步上云"与"完全不用大模型"之间的中间路径：强 VLM 在任务开始时拆解一次计划，此后只在里程碑处低频核实与修订，由四个触发器（步数间隔 / 子任务达成 / 停滞 / 完成被拦）做纯逻辑去抖，把预算控制在**约 1 + 步数/5 次每任务**。配套的会话记忆文件是检索增强在长程一致性上的落点——它既是小模型每步检索的"已验证事实库"（渲染注入原始任务、经核实的事实、单一当前目标），又是监督者与执行器的解耦接口：**监督者只写经截图核实的事实，执行器只读检索结果**，保证检索到的是真事实而非模型的虚假自述。它还确立了一个架构前提——**任务的全部持久状态都在记忆文件里，对话上下文可丢弃**，这是后面故障恢复能成立的基础。学术上，这种"里程碑级、有状态"的监督填补了 token/步级（离不开高频大模型）与查询级路由（任务内不再纠偏）之间的粒度空档。

**创新点 2——机械反幻觉护栏 + 确定性故障恢复**（图中决策区域）。原则是**能用代码确定性判断的绝不交给小模型推理**：机械价格裁决 + SpecGuard 把区间比较前移到代码、在购买提交点对越界商品硬拦截；单一完成权威堵伪完成（监督者在场看截图独裁、机械到访门让位，两条路径互斥以避免证据更弱的机械门误拦真完成）；确定性恢复对每一类失败都有非概率、不依赖提示词的检测信号与恢复路径，每条可能循环的路径都有有界终止保证——任何执行轨迹都终止于成功、显式失败、人工接管三者之一。护栏同时是 AMSG 检索库的**入库质量门**：只有真正成功的任务才把导航轨迹写回图谱（失败任务的观测整体丢弃），保证被检索的导航知识来自真实成功的经验。

### 2.2 AMSG 空间图谱设计（图 2）

![AMSG 空间图谱设计](../phone_agent/docs/空间图谱设计.png)

**图 2 简要概述**：这是本课题的核心检索引擎，图分三块。**左上"节点与边的语义属性"**：图谱以 `UIState —NEXT_ACTION→ Action —PRODUCES→ UIState` 为基本模式，节点存页面语义（app / page_type / landmarks / affordances 等）而非截图哈希、动作存语义意图而非原始坐标，坐标仅作锚定证据不参与去重，关系上记录 frequency / fail_count / confidence 真实统计。**右上"运行时如何赋予空间感知并驱动执行"**：一次 `locate_and_get_context` 完成页面定位 → 验证上一步 → 目标推断 → Dijkstra 规划 → 缓存 RuntimeDAG → 返回 `mode` 与 `graph_hint`，`mode`（navigate / explore / verify_with_vlm / goal_reached）直接驱动三档调度。**下方"运行时自修复闭环与核心价值"**：快速路径执行 → t+1 后条件验证 → 成功/失败统计 → 边生命周期更新（假设 → 候选 → 提升 → 降级）→ 失效自动降级 → 回退 VLM 重新探索。

这张图对应**创新点 3——自更新空间图谱 + 锚定性三档调度**。我先辨析现有图谱方法的三个根本缺陷，AMSG 各用一条洞察解决：

| 现有缺陷 | AMSG 的设计 |
|---|---|
| 图谱静态、建完即冻结 | **执行本身就是免费的验证数据流**——延迟后条件验证（t+1），用"实际到达哪"而非"以为会到哪"持续自校正 |
| 边是布尔的、无可靠性度量 | **四阶段边生命周期**，只有统计可靠的边进入可执行库，UI 漂移后自动降级、重探索、重提升 |
| 图谱与模型边界一刀切 | **逐边锚定性 + 三档调度**：机械转移走快速路径跳过模型，决策转移只给方向、模型做选择 |

落地为执行循环里的三档调度，也就是"检索结果怎么用"的分级策略：**Fast Path**（检索到可靠的锚定边就直接执行、跳过模型，带后条件检查、失配立即回退）、**Graph Co-pilot**（检索到方向但需模型选元素，图谱给方向、模型做 grounding）、**模型路径**（检索不到知识时完整推理）。一句话对照讲清创新：**PG-Agent 对所有边统一"检索即提示"（永不省调用），WebNavigator 对所有边统一"检索即跳转"（过期就翻车），AMSG 则按每条边的锚定性与可靠性动态决定检索结果是直接执行、还是只给方向**；再加上检索库自更新（边生命周期 + t+1 验证），构成一个"在成功中增长、在失效中收缩"的**自进化检索库**——这正是 AMSG 中 "Active" 的含义。

### 2.3 陌生 App 的图谱构建管线（图 3）

![图谱构建管线](../phone_agent/docs/图谱构建管线.png)

**图 3 简要概述**：检索库不是凭空来的，这张图是 AMSG 面对一个全新 App 从零建图、再持续自更新的闭环，分**离线五阶段 + 在线一阶段**。离线部分：①**App 引导**（安全采样、强 VLM 推断领域并产出 draft profile，未确认前不可入图）；②**分轮焦点探索**（强 VLM 规划器与 GUI 模型执行器分离，按覆盖缺口分轮，配防御栈对抗弹窗 / 广告 / 验证码）；③**Staging 规范化**（语义签名去重、过滤瞬态页、候选转移打包）；④**人工审核门**（Gradio 逐条审核，未通过不得进入正式图谱）；⑤**批准入图**（仅审核通过者以 MERGE 写入 Neo4j，`lifecycle_stage=hypothesis`，对运行时 Agent 暂不可见，仍须在线验证才提升）。在线部分：⑥**自动持久化与自进化**——主程序执行结束触发，任务成功才暂存 → 质量门 → 落库，并按边生命周期不断优化图谱效果。

这条管线说明了图谱区域"自更新"的来源：**离线管线解决冷启动**（让一个陌生 App 快速拥有初始图谱），**在线持久化解决持续强化**（每次成功任务回填新转移、校正可靠性）。两道质量门（人工审核 + 任务成功）共同保证被检索的导航知识可信。

## 三、当前进展

我把进展分成"已完成"和"进行中"如实汇报。

### 已完成

1. **四类检索通道均已实现并接入执行循环**：图结构检索、向量检索、按需检索、记忆事实检索四条通道全部落地；三个创新点的设计均已落到单一职责的实现模块。
2. **空间图谱自动化建图管线搭建完成**，可快速探索新的 App。
3. **系统已在淘宝、京东两个真实电商应用完成端到端验证**，覆盖搜索、筛选、详情、规格选择、加购的核心购物链路，京东侧还打通了秒送外卖链路。
4. **多模型、多平台支持已实现**：通过模型协议桥支持 AutoGLM、UI-TARS、Qwen-VL、MAI-UI、GUI-Owl 五个 GUI 模型家族；通过设备抽象覆盖 Android、HarmonyOS、iOS。
5. **WebUI 可视化已实现**，与 CLI 共享同一编排入口，实时展示每步截图、模型思考流、调度路径与后条件验证结果。
6. **实验有效性鉴别机制已就绪**：尤其设计了 provider 链鉴别机制，防止"强 VLM 监督"组在配置缺失时静默退化成小模型自监督、抹平消融对比。
7. **学位论文初稿已成稿**（除实验部分）。

### 进行中

**三组消融实验的环境、任务集、指标体系已确定，正进行真机批量实验采集量化数据**：

- **实验一（核心）三档消融矩阵**：纯小模型基线 / 里程碑监督 / 每步规划上界，在"成功率—延迟—云调用次数"三维上对比，验证低频监督能否以远低于每步规划的成本达到接近的可靠性。
- **实验二 护栏消融**：逐项关闭护栏，度量对应失败模式的发生率回升与有界终止是否被破坏。
- **实验三 检索增强（图谱）消融**：图谱检索开/关、跨域先验开/关，观察 Fast Path 命中率、延迟演化与 UI 漂移后检索库的自修复过程。

## 结语

我的工作论证的是一条工程方法论：**端侧小模型的能力短板，可以通过检索增强来弥补**——把小模型不具备、记不住的导航知识、偏好知识与长程事实，沉淀成可检索、能自更新、有质量保障的外部知识库，在每个决策点检索出来增强它；再用确定性的护栏与低频监督，保障这条"检索 → 决策 → 执行"链路在高风险购物场景下安全可靠。这一"以检索换能力、以结构换可靠"的思路，相比依赖模型规模扩张或寄望模型自我修正，对资源受限的端侧智能体系统更有参考价值。

设计与系统实现已经完成、真机链路已经打通，目前正集中精力完成实验数据的采集与回填。请各位老师批评指正，谢谢。
