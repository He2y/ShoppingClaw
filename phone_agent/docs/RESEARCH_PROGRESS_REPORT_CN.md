# 手机原生主动购物助手研究进展汇报

> 基于 `phone_agent/docs/ARCHITECTURE_CN.md`、`phone_agent/docs/AMSG_DESIGN.md` 与当前代码实现整理。
> 本文面向工作汇报，重点展示研究进展、用户价值、当前不足与未来方向，避免展开底层技术参数。

## 0. 结论

当前项目已经完成从“通用手机 GUI 执行器”到“购物任务智能体原型”的关键跃迁：系统不再只是让模型逐步看图点击，而是形成了一个由小型 GUI 模型、低频强 VLM 监督、确定性购物安全护栏、跨任务空间图谱和离线建图管线组成的闭环系统。

从第一性原则看，购物助手的核心目标不是“替用户点击按钮”，而是“在用户信任的边界内，持续降低购物决策和操作成本”。目前项目在“可靠执行购物流程”上已经形成可汇报的研究成果；但距离“手机原生的主动购物助手”仍有差距，主要缺口在主动需求识别、商品决策质量、跨平台比价、用户授权协议、长期个性化和系统化评测。

下一阶段不应只继续优化点击成功率，而应把研究重心前移到“为什么买、何时买、买哪个、是否值得买、是否安全买”。执行能力是底座，主动购物助手的上层价值来自决策与信任。

## 1. 研究命题

手机购物场景有三个本质难点：

1. **环境不可控**：购物 App 没有稳定 DOM，页面受版本、广告、弹窗、登录态、库存、活动和 A/B 测试影响。
2. **模型不可靠**：小型 GUI 模型适合做屏幕 grounding，但在长任务、价格判断、完成判定和约束遵守上容易遗忘或幻觉。
3. **交易高风险**：购物不是普通导航任务，错误点击可能触发加购、结算、支付、地址修改或隐私暴露。

因此，本项目的核心研究问题可以概括为：

**如何让端侧可部署的小模型，在真实购物 App 的长程任务中，获得接近强模型的可靠性，同时保持低延迟、可恢复、可审计和可控的交易边界。**

项目的当前答案不是把所有决策交给云端强模型，而是采用“非对称权威”架构：

- 小模型负责高频屏幕操作。
- 强 VLM 只在任务拆解、里程碑修订和完成核实时低频介入。
- 代码护栏负责确定性判断，如价格范围、提交风险和完成证据。
- 空间图谱负责跨任务复用已验证的机械导航经验。
- 用户或人工审核门负责交易、登录、验证码和离线图谱质量边界。

## 2. 已完成研究进展

### 2.1 手机 GUI 执行闭环已经成型

项目已实现完整的“截图感知 -> 页面理解 -> 任务计划 -> 模型推理 -> 动作执行 -> 结果验证 -> 轨迹记录”闭环。该闭环支持 Android、HarmonyOS 与 iOS，并通过 CLI 与 WebUI 暴露给用户。

**为什么重要**：购物任务不是单步点击，而是跨多个页面的长程过程。没有稳定闭环，就无法讨论可靠性、恢复、记忆和图谱学习。

**对用户的影响**：用户可以用自然语言发起购物任务，系统能够持续观察手机屏幕、推进步骤，并在异常、验证或高风险页面出现时中断或接管，而不是一次性输出不可执行的建议。

### 2.2 形成“小模型执行 + 强 VLM 低频监督”的混合智能体架构

系统将强 VLM 从“每步决策者”降级为“低频监督者”：任务开始时拆解目标，任务过程中在里程碑处修订计划，结束时核实是否真的完成。小型 GUI 模型仍负责每步屏幕 grounding 和动作生成。

**为什么重要**：强模型每步调用虽然更稳，但成本、延迟和端侧部署目标冲突；纯小模型又容易在长任务中遗忘、绕路或伪完成。低频监督把强模型用在最值钱的位置。

**对用户的影响**：系统既保留端侧执行的响应速度，又降低长程任务跑偏、误判完成和重复绕路的概率。

### 2.3 会话记忆文件解决长任务焦点丢失

项目引入单任务级的会话记忆文件，将原始任务、子任务进度、已验证事实和当前目标持久化。模型对话上下文可以被压缩或重置，但任务锚点不丢。

**为什么重要**：购物任务常常超过十几步，纯聊天历史会迅速变脏。把“事实状态”从“对话文本”中分离出来，是长程稳定性的基础。

**对用户的影响**：系统在被弹窗、登录、搜索失败或模型空响应打断后，可以基于稳定记忆回到当前目标，而不是忘记用户到底要买什么。

### 2.4 购物安全护栏成为一等系统能力

项目已经把购物中的关键安全约束从 prompt 中拿出来，落到确定性代码里。包括预算区间解析、商品价格拦截、规格选择风险、结算/支付页识别、完成判定和人工接管。

**为什么重要**：价格比较、是否越界、是否已到达目标页面，这些不应该由小模型自由判断。购物安全必须是系统属性，而不是模型“尽量遵守”的建议。

**对用户的影响**：当商品价格不符合预算、价格尚未读取、进入结算或验证页面时，系统会阻止危险推进或要求用户确认，降低误买、误提交和隐私泄露风险。

### 2.5 AMSG 空间图谱从“路径记忆”升级为“自进化动作库”

项目提出并实现了主动移动空间图谱 AMSG。图谱节点不存截图哈希，而存页面语义状态；动作不以坐标作为唯一身份，而以意图和后条件组织；边记录成功与失败，形成生命周期。

图谱还区分两类转移：

- **锚定转移**：如首页进入搜索，位置和语义稳定，可复用。
- **非锚定转移**：如从搜索结果选择哪个商品，必须由模型看当前屏幕和任务目标决定。

**为什么重要**：传统页面图谱要么只是给模型提供 RAG 提示，要么过度信任静态路径。AMSG 的关键贡献是让每条边独立决定控制强度：可靠且机械的边走快速路径，不确定或内容相关的边交给模型。

**对用户的影响**：重复的机械导航会越来越快，App 更新导致路径失效时也能通过失败统计自动降级，避免长期使用中的“越学越脏”。

### 2.6 陌生购物 App 的建图管线已形成

项目已经形成面向陌生 App 的五阶段建图流程：App 引导、焦点探索、staging 规范化、人工审核、批准入图。离线探索产物不会直接污染正式图谱，必须经过审核门。

该流程已经覆盖淘宝核心购物链路，并扩展到京东及秒送/外卖链路，说明图谱不是单 App 硬编码，而是开始具备同域迁移能力。

**为什么重要**：购物助手不可能只服务一个 App。可复制的建图流程比一次性采集数据更有研究价值。

**对用户的影响**：未来接入新购物 App 时，可以通过结构化探索和审核逐步获得可用导航经验，而不是每个 App 从零写规则。

### 2.7 已具备工程验证与消融基础

代码库中已有针对图谱生命周期、运行时图谱、领域先验、里程碑监督、SpecGuard、会话记忆、WebUI 遥测等模块的测试。系统也保留了纯小模型、里程碑监督、每步强规划等消融开关。

**为什么重要**：研究系统不能只展示 demo，需要能解释“哪个机制带来了什么收益”。当前代码已经为后续论文式实验和工作汇报中的量化表格打下基础。

**对用户的影响**：后续可以用真实指标回答“更快了多少、少错了多少、少需要几次人工接管”，从而指导产品形态，而不是凭直觉调参。

## 3. 当前成果的研究价值

### 3.1 从模型能力转向系统可靠性

当前成果证明：购物 GUI Agent 的可靠性不只来自更大的模型，也来自系统把任务拆成不同性质的判断，并交给合适的主体处理。

这是一条适合端侧智能体的路线。小模型处理高频视觉 grounding，强模型处理低频语义监督，代码处理确定性边界，图谱处理跨任务经验复用。

### 3.2 从静态页面图谱转向活的经验系统

AMSG 的研究价值在于把页面图谱从“离线建完的地图”改造成“持续学习的动作库”。边不是存在即可信，而是需要经过验证、提升、降级和再学习。

这对购物场景尤其重要，因为购物 App 的 UI、活动入口、结算流程和商品卡片变化频繁。图谱必须能自我修复，否则会变成长期风险源。

### 3.3 从提示工程转向交易安全架构

购物任务的安全边界不能只写在 prompt 里。项目已经把价格、规格、结算、支付、完成判定等关键约束转为结构化状态和代码护栏。

这使系统具备更清晰的责任划分：模型可以建议，系统必须审计，用户保留最终授权。

## 4. 与“主动购物助手”目标的差距

当前系统更准确的定位是：**面向购物场景的手机 GUI 任务执行智能体**。它已经能完成“用户明确下达任务后，代替用户操作购物 App”的核心链路。

但“手机原生的主动购物助手”要求更高。它应该在用户没有完整指令时，也能围绕需求、预算、偏好、时机、风险和授权做持续协助。当前主要不足如下。

### 4.1 主动性不足

目前系统以用户显式命令为起点，如“帮我买一个蓝牙耳机”。它还不能稳定地从用户日常行为、历史偏好、价格变化、库存变化、节日场景或补货周期中主动发现购物机会。

未来的主动助手不应频繁打扰用户，而应在高置信、低干扰、可解释的场景中提出建议，例如“你常买的咖啡豆降价到历史低位，要不要加入购物车等你确认？”

### 4.2 商品决策能力不足

当前系统强在执行路径，而不是判断商品是否真的值得买。它可以搜索、筛选、打开商品、加购，但尚未形成系统性的商品理解能力。

关键缺口包括：

- 跨商品参数对比。
- 评价质量与虚假评价识别。
- 店铺信誉、售后、发货地、保价和退换政策理解。
- 优惠券、满减、会员价和配送费的总成本计算。
- 跨 App 比价与替代品推荐。

这意味着系统目前更像“会操作手机的执行助手”，还不是“会帮用户做购物判断的消费决策助手”。

### 4.3 个性化仍然偏浅

系统已有用户记忆与偏好填充能力，但购物偏好远比简单槽位复杂。真正的购物助手需要理解用户长期价值函数：品牌偏好、价格敏感度、质量偏好、配送速度、环保倾向、售后偏好、家庭成员需求和冲动消费风险。

如果没有长期偏好建模，主动推荐会很容易变成噪声，甚至损害用户信任。

### 4.4 冷启动与图谱覆盖仍有限

AMSG 已经解决“如何让图谱持续进化”的方法问题，但新 App 或新频道在缺少 promoted 边时仍然偏冷。当前 RuntimeDAG 的缓存优化在真实运行中也有局限：后条件验证与跳过分类器之间存在结构性矛盾，导致设计上的快路径并不总能兑现。

这不是小问题。主动助手必须长期运行在不断变化的 App 中，如果冷启动成本过高或图谱命中率不稳定，用户会感知为“有时聪明、有时突然变笨”。

### 4.5 缺少系统化购物评测

目前已有真机验证和单元测试，但还需要形成面向工作汇报和论文的统一评测框架。

建议至少评估以下维度：

- 任务成功率。
- 平均完成步数与耗时。
- 强 VLM 调用次数。
- 人工接管次数。
- 价格/规格/结算安全违规次数。
- App 更新后的自修复速度。
- 新 App 冷启动到可用图谱的成本。
- 用户是否理解并信任系统建议。

没有这些指标，研究成果容易停留在“看起来能跑”的 demo 层面。

### 4.6 用户授权与信任协议尚未产品化

购物助手必须明确哪些事可以自动做，哪些事必须征得用户确认。当前系统已经对高风险页面采取保守策略，但还需要更完整的授权模型。

例如：

- 搜索、浏览、收藏、加入购物车可以分级授权。
- 提交订单、支付、地址变更必须用户确认。
- 主动推荐必须解释触发原因。
- 每次高风险动作都应能回放“为什么系统认为这一步安全”。

主动购物助手的关键不是自动化越多越好，而是用户能放心地把多少决策委托给它。

### 4.7 原生手机体验还不完整

当前系统有 CLI 和 WebUI，但“手机原生助手”还需要更贴近用户日常使用的交互形态：系统级悬浮窗、通知、快捷确认、任务暂停与恢复、订单跟踪、价格监控、售后提醒等。

如果交互入口仍主要是开发者工具，研究价值可以成立，但产品价值难以完全体现。

## 5. 未来研究方向

### 5.1 从“任务执行”升级为“购物意图管理”

下一阶段应建立购物意图层，把用户需求从一次性命令扩展为可维护的长期状态。

研究问题：

- 如何识别用户是“立即购买”还是“持续观察”？
- 如何表示预算、偏好、可替代方案和硬性约束？
- 如何在不打扰用户的情况下触发主动建议？
- 如何让用户快速修改或撤销长期购物意图？

预期产出：一个 Shopping Intent Store，记录待购、常购、观察、替代和已拒绝的商品意图，并与手机通知和任务执行闭环连接。

### 5.2 建立商品决策与价值评估层

执行系统之上需要一个“买不买、买哪个、为什么”的决策层。它不直接点击屏幕，而是综合商品信息、价格、评价、店铺、优惠和用户偏好，给出可解释建议。

研究问题：

- 如何从原生 App 页面稳定抽取商品结构化信息？
- 如何判断评论可信度和商品风险？
- 如何计算总拥有成本，而不只看标价？
- 如何在多个 App 之间比较同类商品？
- 如何让推荐理由足够短，但又能支撑信任？

预期产出：商品候选集、购物价值函数、跨 App 比较器和解释模板。

### 5.3 构建交易安全与授权协议

未来的主动助手必须有明确的自治等级。不是所有动作都需要用户确认，但每个高风险动作都必须可解释、可暂停、可回滚。

建议定义四级授权：

1. 浏览级：搜索、打开页面、读取信息。
2. 准备级：筛选、比较、收藏、加入购物车。
3. 待确认级：选择规格、应用优惠、生成订单草稿。
4. 禁止自动级：支付、提交订单、修改地址、处理验证码。

研究重点不是让系统“敢点支付”，而是让用户知道系统永远不会越过授权边界。

### 5.4 强化 AMSG 的冷启动与跨 App 泛化

AMSG 下一步应重点解决“新 App 早期不可用”和“图谱优化收益不稳定”的问题。

可研究方向：

- 离线审核边是否可以在低风险场景中更快进入可用态。
- 用轻量视觉/结构信号替代部分昂贵分类调用。
- 将同域结构先验从文本提示升级为可验证的候选计划。
- 让 RuntimeDAG 真正复用路径游标，同时不破坏后条件验证真实性。
- 自动发现新页面类型，并把 schema 演化纳入审核流。

目标不是让图谱完全替代模型，而是让图谱在可验证、低风险、重复性高的部分稳定省掉模型负担。

### 5.5 建立长期个性化与隐私保护机制

主动购物助手需要知道用户偏好，但购物偏好高度敏感。下一阶段应研究“端侧优先”的个性化记忆。

研究问题：

- 哪些偏好必须本地保存？
- 哪些偏好可以匿名统计？
- 如何让用户查看、编辑、删除购物记忆？
- 如何区分长期偏好与一次性需求？
- 如何避免系统把用户过去的冲动消费当成未来偏好？

用户影响：个性化越强，越需要可控、可解释和可删除。

### 5.6 设计购物 Agent 专用评测基准

通用 GUI benchmark 难以覆盖购物任务的交易风险。建议构建面向购物助手的评测集。

任务类型可以包括：

- 指定预算购买。
- 指定规格加购。
- 跨商品比较。
- 优惠券/满减计算。
- 避免越界价格。
- 登录/验证码接管。
- App 更新后的路径修复。
- 新频道冷启动建图。
- 主动降价提醒与用户确认。

评测指标不只看成功率，还要看风险违规、人工接管、解释质量、延迟和用户满意度。

### 5.7 打磨原生交互体验

如果目标是手机原生主动购物助手，交互设计必须前置。

建议重点研究：

- 低打扰主动提醒。
- 一句话确认或拒绝。
- 操作预览与关键步骤回放。
- 高风险动作的明确确认。
- 失败时给出下一步，而不是只报错。
- 用户可随时暂停、接管、恢复。

对用户来说，可靠性不只是任务最终成功，也包括过程中“我知道它在做什么、为什么这么做、何时会停下来”。

## 6. 建议汇报主线

汇报时建议不要按代码模块展开，而按研究问题展开：

1. **问题**：真实手机购物任务为什么难？环境变化、小模型不可靠、交易高风险。
2. **方法**：非对称权威架构，把执行、监督、护栏和图谱分别交给最合适的主体。
3. **进展**：已完成手机闭环、里程碑监督、会话记忆、购物安全护栏、AMSG、陌生 App 建图与 WebUI 可观测。
4. **证据**：淘宝和京东真实 App 验证，代码中已有测试与消融开关。
5. **诚实边界**：当前是购物任务执行智能体，还不是完整主动购物助手。
6. **下一步**：补商品决策、主动意图、授权协议、长期个性化和系统评测。

一句话总结：

**本项目的当前贡献，是把手机购物 Agent 从“模型看图点击”推进到“可监督、可恢复、可学习、可审计的购物执行系统”；下一阶段要把它继续推进到“理解需求、比较商品、把握时机、尊重授权的主动购物助手”。**
