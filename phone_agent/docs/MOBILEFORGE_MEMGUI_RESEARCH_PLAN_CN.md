# Shopping-Agent 研究方案：面向手机购物 App 的稳定操作优化与主动助手拓展

> **版本**：2026-06-28
> **用途**：汇报展示版。面向不熟悉本项目的听众，先介绍现有系统设计，再说明 MobileForge 与 MemGUI-Agent 对现有模块的优化价值，最后将“主动专业购物助手”作为未来拓展方向单独展开。
> **依据**：`phone_agent/docs/ARCHITECTURE_CN.md`、`phone_agent/docs/AMSG_DESIGN.md`、`references/MobileForge.pdf`、`references/MemGUI-Agent.pdf`。

---

## 摘要

Shopping-Agent 当前定位为手机购物场景下的 GUI 操作智能体，核心目标是在真实 App 中稳定完成搜索、筛选、商品浏览、规格选择、加购与结算前检查等长程操作。系统采用“小型 GUI 模型高频执行 + 强 VLM 低频监督 + AMSG 空间图谱导航 + 机械护栏 + 会话记忆”的混合架构，重点解决购物 App 自动化中的可靠性、低延迟和安全边界问题。

MobileForge 和 MemGUI-Agent 的最新工作对本项目的直接价值不在于替换当前方案，而在于进一步增强两个关键短板：

1. **陌生购物 App 适配能力**：借鉴 MobileForge 的真实 App 探索、任务挖掘和分层反馈机制，构建面向 AMSG 的安全探索与图谱冷启动流程。
2. **长程任务上下文稳定性**：借鉴 MemGUI-Agent 的 Context-as-Action 思想，构建可验证的上下文动作，使价格、规格、页面事实和任务进度能够被可靠写入会话记忆。

在现有系统优化完成后，项目可进一步拓展为主动专业购物助手。该拓展方向将引入购物意图建模、商品证据账本、多目标决策、主动策略和授权边界，使系统从“稳定操作购物 App”升级为“辅助用户做购物决策”。

## 1  现有系统设计

### 1.1  研究场景与核心问题

本项目面向手机购物 App 的自动化操作场景。购物 App 与网页自动化或标准桌面 UI 不同，主要挑战包括：

- 无稳定 DOM，主要依赖截图、视觉理解和坐标点击。
- 页面受广告、弹窗、登录态、活动页、App 更新和设备分辨率影响。
- 任务链路长，通常包含搜索、筛选、商品详情、SKU、购物车、结算前确认等多个阶段。
- 商品价格、规格、优惠和购买状态具有高风险属性，不能完全依赖模型自由判断。
- 通用 GUI 模型容易出现焦点漂移、价格误判、任务伪完成和重复探索。

因此，现有系统的研究问题可以概括为：

> 如何让可端侧部署的小型 GUI 模型，在真实购物 App 的长程任务中获得接近强 VLM 的可靠性，同时控制云端调用成本、响应延迟和高风险操作边界？

### 1.2  总体架构

系统主循环位于 `phone_agent/agent.py`，每个任务按照如下闭环执行：

```text
任务输入
  -> 截图
  -> 记忆检索
  -> 历史与上下文构建
  -> VLM/GUI 模型调用
  -> 动作解析
  -> 坐标归一化
  -> 动作执行
  -> 轨迹记录
  -> 记忆与图谱更新
  -> 下一轮截图
```

该闭环的关键特点是：模型并不独立承担所有决策。系统把不同性质的判断拆分给不同组件，使 GUI grounding、任务规划、价格判断、安全拦截和路径复用分别由最合适的机制负责。

### 1.3  非对称权威机制

`ARCHITECTURE_CN.md` 中的核心设计原则是**非对称权威**。系统不追求单个模型完成全部判断，而是按照决策类型分配权威。

| 决策类型 | 当前权威 | 主要模块 | 作用 |
|---|---|---|---|
| 当前屏幕元素定位 | 小型 GUI 模型 | `phone_agent/model/`, `phone_agent/actions/` | 高频执行，完成截图到动作的 grounding |
| 任务拆解与里程碑修订 | 强 VLM 监督者 | `milestone_supervisor.py`, `task_plan.py` | 低频介入，纠正长程任务中的语义漂移 |
| 数字与硬约束判断 | 机械护栏 | `core/spec_guard.py`, `verification_detector.py` | 解析价格、预算、规格和完成证据，降低幻觉风险 |
| 结构化导航复用 | AMSG 空间图谱 | `spatial/`, `memory/graph_store.py` | 复用经验证的页面转移和机械导航路径 |
| 单任务状态保持 | 会话记忆文件 | `session_memory_file.py` | 记录原始目标、子任务进度和已验证事实 |

这一机制使系统在购物 App 中既能保持模型灵活性，也能在高风险判断上使用确定性逻辑兜底。

### 1.4  AMSG 空间图谱

AMSG（主动移动空间图谱）是现有系统区别于普通 ReAct Agent 的关键模块。它不存储静态页面截图，而是存储可复用的语义页面和语义动作。

```text
PageState = (app, page_type, landmarks, affordances, slots, risk_level)
Action = (type, intent, semantic_target, postcondition, lifecycle_stage)

(UIState) -[NEXT_ACTION]-> (Action) -[PRODUCES]-> (UIState)
```

AMSG 的核心机制包括：

| 机制 | 设计含义 | 系统价值 |
|---|---|---|
| 语义去重 | 将同类页面合并，例如不同关键词的搜索结果页都归为 `search_result` | 避免图谱因商品内容变化而爆炸 |
| 边生命周期 | 对每条转移记录成功率、失败率、验证次数和生命周期阶段 | 只有可靠边才能进入执行候选 |
| 锚定性分类 | 区分图谱可独立执行的边和必须交给模型看屏幕的边 | 在低风险机械步骤加速，在内容敏感步骤保持模型判断 |
| 后条件验证 | 下一步用真实页面状态验证上一动作是否达成预期 | 避免图谱根据模型假设自我强化 |
| 多 App 组织 | 通过 app/domain 分层检索图谱结构 | 支持同类购物 App 的结构先验迁移 |

### 1.5  三档调度策略

系统根据图谱边的可靠性、锚定性和风险等级，在每一步选择不同执行路径。

| 调度档位 | 触发条件 | 行为 |
|---|---|---|
| Fast Path | promoted、锚定、低风险、有坐标或复合动作 | 跳过模型，直接执行机械导航，并做后条件检查 |
| Graph Co-pilot | 图谱知道下一步方向，但目标需要看当前屏幕 | 图谱提供 `graph_hint`，小模型负责 grounding |
| Model Path | 图谱未知、非锚定、高风险或验证失败 | 完整模型推理 |

三档调度的目标不是让图谱完全替代模型，而是在可复用、低风险、已验证的步骤上减少模型调用；在商品选择、SKU 选择、优惠判断、结算前检查等步骤上继续保留模型和护栏的共同判断。

### 1.6  会话记忆与机械护栏

长程购物任务容易出现上下文遗忘和任务目标漂移。现有系统通过 `SessionMemoryFile` 固化关键状态：

- `original_task`：原始任务描述，作为抗漂移锚点。
- `subtasks`：任务拆解后的阶段状态。
- `verified_facts`：已确认的价格、规格、筛选条件、加购状态等事实。
- `revisions`：强 VLM 里程碑监督产生的修订记录。

机械护栏承担模型不擅长的确定性判断：

- 价格解析与预算比较。
- 商品规格约束校验。
- 购买提交点拦截。
- 完成证据判断。
- 空响应与不可解析动作恢复。

这部分设计使系统具备“操作安全性”：模型可以提出动作，但高风险动作必须通过机械规则和页面证据校验。

### 1.7  阶段性成果与能力边界

现有系统已经形成一套面向购物 App 的稳定操作底座：

- 能在真实设备和真实购物 App 中执行长程 GUI 操作。
- 能通过强 VLM 低频监督降低小模型长程漂移。
- 能通过 AMSG 复用购物 App 中的机械导航路径。
- 能通过机械护栏减少价格、预算、完成状态等关键幻觉。
- 能通过轨迹和图谱持久化逐步积累跨任务导航经验。

当前系统的主要能力边界是：它更偏向“稳定执行购物 App 操作”，尚未系统性建模购物意图、候选商品比较、购买风险评估和主动推荐策略。这一能力边界不影响现有工作的价值，但决定了下一阶段优化应分为两层：

1. **近期优化**：继续提升现有 GUI 操作系统的泛化性、稳定性和长程记忆能力。
2. **未来拓展**：在稳定操作底座之上构建主动专业购物助手能力。

## 2  基于 MobileForge 与 MemGUI-Agent 的现有系统优化方向

MobileForge 与 MemGUI-Agent 均关注移动 GUI Agent 的可靠性提升，但二者对本项目的价值应落到现有系统模块，而不是直接改变项目主线。结合 Shopping-Agent 当前架构，二者可分别服务于“陌生 App 适配”和“长程上下文管理”两个优化方向。

### 2.1  优化方向一：AMSG-Gym 陌生购物 App 探索机制

MobileForge 的核心思想是 annotation-free adaptation：在真实目标 App 中自动探索、挖掘可执行任务、执行 rollout，并利用分层反馈改进策略。

在本项目中，该思想适合落到 AMSG，而不是直接用于训练一个面向单个购物 App 的强化学习 policy。原因是购物 App 更新频繁、页面活动态复杂、高风险动作多，直接对具体 App 做强化学习容易过拟合当前版本，也会带来较高安全成本。

更合适的落地形式是 **AMSG-Gym**：

```text
陌生购物 App
  -> 安全探索首页、搜索、商品详情、SKU、购物车等页面
  -> 挖掘可执行购物流程片段
  -> rollout 验证页面转移是否成立
  -> 生成分层反馈
  -> 更新 AMSG schema、候选边、生命周期和探索策略
```

AMSG-Gym 的目标是提高图谱冷启动能力，使系统在新购物 App、新版本页面、新促销入口或新弹窗状态下，更快建立可验证的导航知识。

| MobileForge 概念 | Shopping-Agent 落点 | 预期效果 |
|---|---|---|
| Target-app exploration | `phone_agent/adaptation/amsg_gym.py` | 在陌生购物 App 中探索关键页面类型 |
| Curriculum mining | `phone_agent/adaptation/curriculum.py` | 自动生成覆盖首页、搜索、结果、详情、SKU、购物车的探索任务 |
| Rollout feedback | `phone_agent/adaptation/critic.py` | 判断转移是否真实有效、是否安全、是否具备复用价值 |
| Policy improvement | AMSG 边生命周期与 ActionAdvisor | 不直接训练 policy，而是改进图谱提示和可执行边集合 |
| Experience export | `dataset_exporter.py` | 将高质量轨迹作为后续数据资产 |

### 2.2  优化方向二：分层反馈驱动的图谱生命周期更新

现有 AMSG 已经具备后条件验证和边生命周期机制。MobileForge 的分层反馈思想可以进一步增强图谱更新质量，使每条探索经验不只产生“成功/失败”的二元信号，而是形成多层反馈。

| 反馈层级 | 反馈内容 | 对 AMSG 的更新 |
|---|---|---|
| 动作级反馈 | 点击目标是否正确、是否触发预期控件 | 更新动作坐标证据和锚定性 |
| 页面级反馈 | 页面类型是否符合预期、是否出现弹窗或登录态 | 更新 PageState、risk_level 和异常状态标签 |
| 流程级反馈 | 搜索到详情、详情到 SKU、SKU 到购物车等链路是否闭合 | 更新边成功率、失败率和生命周期 |
| 任务级反馈 | 探索任务是否完整覆盖目标购物流程 | 更新探索 curriculum 和未覆盖页面清单 |
| 安全级反馈 | 是否接近提交订单、支付、地址修改等高风险动作 | 更新动作黑名单和人工确认门 |

该优化使 AMSG 从“被动记录成功轨迹”升级为“能够利用探索反馈自我修复的图谱系统”。这与现有 AMSG 设计方向一致，不会破坏三档调度和后条件验证红线。

### 2.3  优化方向三：Verified Context Actions 长程上下文动作

MemGUI-Agent 的核心思想是 Context-as-Action：上下文管理不再只是提示词压缩，而是 Agent 行为空间的一部分。模型可以主动决定何时记录事实、何时折叠历史、何时保留关键 UI 状态。

Shopping-Agent 已有 `SessionMemoryFile`，但当前记忆更新更偏结果记录。借鉴 MemGUI-Agent 后，可引入 **Verified Context Actions (VCA)**，把上下文更新显式建模为可审计动作。

```text
模型/监督者提出上下文动作
  -> ContextCommitter 校验证据来源
  -> 低风险事实自动提交
  -> 高风险事实需要截图、机械解析或强 VLM 证据
  -> 写入 SessionMemoryFile
```

可支持的上下文动作包括：

| 上下文动作 | 含义 | 验证要求 |
|---|---|---|
| `remember_task_anchor` | 记录原始任务和当前阶段目标 | 来自任务输入或强 VLM 计划 |
| `update_verified_price` | 更新商品价格或券后价 | 必须来自机械价格解析或截图证据 |
| `update_selected_spec` | 更新已选择规格 | 必须来自规格页或当前页面证据 |
| `mark_subtask_done` | 标记子任务完成 | 必须通过页面状态或里程碑监督验证 |
| `fold_history_segment` | 折叠已完成的历史片段 | 片段中的关键事实必须已写入结构化记忆 |
| `record_blocker` | 记录登录、弹窗、无库存等阻塞状态 | 来自页面分类或截图证据 |
| `record_user_preference` | 记录低风险用户偏好 | 高敏偏好需要用户确认 |

VCA 的价值在于把“记忆”从文本摘要变成结构化、带证据、可回滚的系统状态，减少长程任务中的事实丢失和事实污染。

### 2.4  优化方向四：会话记忆的证据分区

结合 MemGUI-Agent 的上下文管理思想，现有 `SessionMemoryFile` 可进一步拆分为不同证据区，避免所有信息混在同一段摘要中。

```text
SessionMemoryFile
  original_task
  current_milestone
  subtasks
  verified_facts
    price_facts
    spec_facts
    page_facts
    action_facts
  blockers
  context_actions
  folded_history
```

这种结构能直接支持三类系统能力：

1. **更稳定的模型提示**：每步只注入当前目标和必要事实，减少历史噪声。
2. **更可靠的护栏判断**：SpecGuard 可以直接读取结构化价格、规格和动作事实。
3. **更可审计的轨迹回放**：每个关键事实都有对应的上下文动作和证据来源。

### 2.5  优化方向五：训练数据与评估资产建设

MobileForge 的探索轨迹和 MemGUI-Agent 的上下文动作都可以沉淀为数据资产，但数据导出应作为现有系统优化的副产物，而不是第一目标。

可形成三类资产：

| 数据资产 | 来源 | 用途 |
|---|---|---|
| 图谱探索轨迹 | AMSG-Gym rollout | 分析陌生 App 冷启动、训练页面转移判断器 |
| 上下文动作序列 | VCA 提交记录 | 训练或评估长程记忆管理能力 |
| 失败恢复案例 | 后条件失配、弹窗、登录态、价格越界 | 构建鲁棒性测试集 |

评估指标也应围绕现有系统优化展开：

- 任务完成率。
- 平均步数与平均延迟。
- 强 VLM 调用次数。
- 陌生 App 页面覆盖率。
- AMSG promoted 边增长质量。
- 后条件验证成功率。
- 长程事实保留率。
- 价格、规格和完成状态错误率。
- 高风险动作误触发次数。

## 3  实施计划

### 3.1  总体路线

实施优先级以“增强现有操作系统”为主，先让 Shopping-Agent 在更多购物 App、更长任务、更复杂页面状态下保持稳定，再为未来主动购物助手建设数据和能力底座。

```text
阶段一：AMSG-Gym 最小闭环
  -> 实现陌生购物 App 安全探索、任务生成和 rollout 反馈

阶段二：Verified Context Actions
  -> 将上下文更新显式化、结构化、可验证

阶段三：图谱与记忆联合优化
  -> 用探索反馈更新 AMSG，用 VCA 保持长程任务事实

阶段四：评估与数据资产沉淀
  -> 建立可复现实验、消融矩阵和高质量轨迹导出
```

### 3.2  阶段一：AMSG-Gym 最小闭环

目标：让系统能够在陌生购物 App 或新版本页面中安全探索，生成可审核的图谱候选边。

新增模块：

```text
phone_agent/adaptation/
  __init__.py
  amsg_gym.py
  curriculum.py
  critic.py
  safety_policy.py
  dataset_exporter.py
```

主要任务：

1. 定义购物 App 探索 curriculum：首页、搜索框、搜索结果、商品详情、SKU、购物车、店铺页、评价页。
2. 限制探索动作边界：禁止提交订单、支付、修改地址等高风险动作。
3. 接入现有页面分类器和后条件验证，判断 rollout 是否达成预期页面。
4. 将探索结果写入 staging 图谱，保持人工审核门和生命周期提升规则。
5. 输出探索覆盖报告，包括页面覆盖、边候选数量、失败原因和风险动作拦截次数。

验收标准：

- 能在至少一个陌生购物 App 或新版本购物 App 中完成安全探索。
- 能生成可审核的 UIState-Action-UIState 候选边。
- 所有候选边进入 `hypothesis` 阶段，不绕过在线验证直接 promoted。
- 高风险动作误触发次数为 0。

### 3.3  阶段二：Verified Context Actions

目标：让长程任务中的关键事实不再依赖历史文本堆叠，而是通过可验证上下文动作写入会话记忆。

新增或改造模块：

```text
phone_agent/context/
  __init__.py
  actions.py
  committer.py
  evidence.py
  compactor.py
```

主要任务：

1. 定义上下文动作 schema，包括事实类型、证据来源、风险等级和提交条件。
2. 实现 `ContextCommitter`，对价格、规格、页面状态和完成状态做证据校验。
3. 扩展 `SessionMemoryFile`，增加 `context_actions`、`folded_history` 和证据分区。
4. 在里程碑监督和每步执行后触发上下文动作提议。
5. 在提示构建阶段只注入当前阶段所需事实，减少无关历史干扰。

验收标准：

- 价格、规格、页面状态等关键事实均有证据来源。
- 历史折叠前，关键事实已经写入结构化记忆。
- 同一任务 30 步以上执行时，原始目标和关键约束不丢失。
- 事实冲突时能够标记冲突并请求重新验证，而不是静默覆盖。

### 3.4  阶段三：图谱与记忆联合优化

目标：让 AMSG-Gym 产生的探索反馈与 VCA 产生的上下文动作共同服务现有执行循环。

联合机制：

| 场景 | AMSG-Gym 作用 | VCA 作用 |
|---|---|---|
| 陌生 App 冷启动 | 探索页面结构和候选转移 | 记录探索中发现的页面事实 |
| 长程购物操作 | 提供经验证的导航提示 | 保持价格、规格、任务阶段和阻塞状态 |
| 后条件失配 | 降级图谱边，生成修复探索任务 | 记录失败原因和当前阻塞 |
| 强 VLM 里程碑修订 | 使用图谱覆盖信息辅助判断下一阶段 | 将修订写入结构化上下文动作 |

预期结果：

- 图谱负责“怎么走”。
- 上下文动作负责“走过后哪些事实成立”。
- 机械护栏负责“哪些动作不能越界”。
- 强 VLM 负责“阶段性计划是否需要修订”。

### 3.5  阶段四：实验设计与消融

实验配置：

| 配置 | AMSG-Gym | VCA | 目标 |
|---|---:|---:|---|
| Current | 否 | 否 | 当前系统基线 |
| +AMSG-Gym | 是 | 否 | 验证陌生购物 App 适配能力 |
| +VCA | 否 | 是 | 验证长程上下文事实保留能力 |
| +AMSG-Gym+VCA | 是 | 是 | 验证图谱探索与上下文动作联合收益 |

核心指标：

| 指标 | 说明 |
|---|---|
| 任务完成率 | 是否完成用户指定购物操作 |
| 平均步数/延迟 | 操作效率和用户等待成本 |
| 强 VLM 调用次数 | 云端成本 |
| 页面覆盖率 | 陌生 App 探索覆盖首页、搜索、详情、SKU 等页面的比例 |
| promoted 边质量 | promoted 边的后续成功率和回退率 |
| 事实保留率 | 长程任务中价格、规格、阶段状态是否保持正确 |
| 事实污染率 | 错误事实被写入记忆的比例 |
| 高风险动作误触发 | 提交订单、支付、地址修改等动作必须为 0 |

### 3.6  时间规划

两周版本：

1. 完成 AMSG-Gym 的探索任务 schema。
2. 完成购物 App 安全探索策略。
3. 完成 VCA 的动作 schema 和 `ContextCommitter` 雏形。
4. 在淘宝或京东以外的一个购物 App 上跑通最小探索闭环。
5. 在现有购物任务中记录价格、规格、页面状态三类上下文动作。

一个月版本：

1. AMSG-Gym 支持分层反馈和 staging 图谱导出。
2. VCA 接入 `SessionMemoryFile` 和提示构建流程。
3. 实现历史折叠前的关键事实提交检查。
4. 完成 Current / +AMSG-Gym / +VCA / +Both 四组消融。
5. 输出陌生 App 适配报告和长程上下文稳定性报告。

三个月版本：

1. 完成多个购物 App 的冷启动探索实验。
2. 形成图谱探索轨迹、上下文动作序列和失败恢复案例三类数据资产。
3. 形成面向论文或中期汇报的系统性消融结果。
4. 将高质量探索经验导出为后续训练或评估数据。
5. 为主动购物助手拓展准备商品证据和任务记忆基础。

### 3.7  风险控制

| 风险 | 控制方式 |
|---|---|
| 探索触发高风险操作 | `safety_policy.py` 禁止提交订单、支付、地址修改等动作 |
| 图谱从失败轨迹中学习错误边 | 所有探索边先进入 staging/hypothesis，经后条件验证和审核后才可提升 |
| 上下文动作写入错误事实 | 高风险事实必须有截图、机械解析或强 VLM 证据 |
| 历史折叠丢失关键信息 | 折叠前检查关键事实是否已结构化提交 |
| 过度依赖新论文概念 | 所有改动必须落到现有执行循环、AMSG、SessionMemoryFile 和 SpecGuard |

## 4  未来拓展：主动专业购物助手

现有优化完成后，系统将具备更稳定的购物 App 操作底座：能适配陌生 App、能保持长程上下文、能积累高质量图谱和任务轨迹。在此基础上，下一阶段可以拓展为主动专业购物助手。

这一章是面向未来的能力升级，不替代第二、三章中的现有系统优化。

### 4.1  拓展动机

稳定操作购物 App 解决的是“能不能完成操作链路”的问题；主动专业购物助手进一步解决“能不能帮助用户做更好的购物决策”的问题。

购物任务通常不只是点击流程，还包含：

- 理解用户购买意图。
- 明确硬约束和软偏好。
- 收集候选商品证据。
- 比较价格、规格、评价、物流、售后和风险。
- 解释推荐理由。
- 在用户授权后执行加购、结算前确认等动作。

### 4.2  Shopping Intelligence Layer

未来可在现有 GUI 操作底座之上增加 **Shopping Intelligence Layer (SIL)**。

```text
用户购物需求
  -> Shopping Intent Graph
  -> Product Evidence Ledger
  -> Shopping Decision Engine
  -> Proactive Shopping Strategy
  -> Trust and Approval Boundary
  -> GUI 操作执行
```

#### 4.2.1  Shopping Intent Graph

将用户自然语言需求结构化为购物意图：

```text
ShoppingIntent = {
  product_category,
  hard_constraints,
  soft_preferences,
  decision_criteria,
  budget_policy,
  risk_tolerance,
  clarification_needed,
  approval_boundary
}
```

该模块用于回答“用户到底想买什么”，例如预算、品类、规格、品牌偏好、配送时效和是否接受预售等。

#### 4.2.2  Product Evidence Ledger

维护候选商品证据账本：

```text
ProductCandidate = {
  title,
  price_raw,
  price_final,
  coupon_info,
  specs,
  seller,
  rating,
  review_signals,
  shipping,
  after_sales,
  risk_flags,
  evidence_refs,
  match_status,
  reject_reason
}
```

该模块用于回答“系统看过哪些商品、证据是什么、为什么保留或淘汰”。

#### 4.2.3  Shopping Decision Engine

对候选商品进行多目标决策：

1. 硬约束过滤：预算、品类、规格、现货、官方店、用户明确要求。
2. 软偏好排序：性价比、评价质量、店铺可靠性、物流时效、售后和风险。
3. 推荐解释：输出推荐、备选和淘汰原因。

输出形式应是可解释建议，而不是直接替用户购买：

```text
推荐 A：符合预算，评价稳定，发货快。
备选 B：价格略高，但售后和品牌更可靠。
淘汰 C：价格低，但店铺风险和评价异常较高。
```

#### 4.2.4  Proactive Shopping Strategy

主动策略模块负责在关键节点给出建议：

- 需求不完整时主动澄清。
- 搜索结果质量差时建议换关键词或换平台。
- 候选商品不满足约束时建议放宽条件。
- 发现优惠、预售、默认勾选服务时提醒用户。
- 发现低价高风险商品时拒绝推荐。
- 购买前生成决策摘要并请求确认。

#### 4.2.5  Trust and Approval Boundary

主动助手必须明确建议权和执行权边界：

| 动作 | 权限边界 |
|---|---|
| 搜索、筛选、打开商品 | 可自动执行 |
| 收集商品证据、比较候选 | 可自动执行 |
| 加入购物车 | 按用户设置，可要求确认 |
| 提交订单、支付、修改地址 | 必须用户显式确认 |
| 记录用户偏好 | 低风险偏好可记录，高敏偏好需确认 |

### 4.3  与现有优化的关系

主动专业购物助手依赖第二、三章的系统优化：

| 未来能力 | 依赖的现有优化 |
|---|---|
| 商品证据账本 | VCA 的可验证事实写入 |
| 跨 App 比价与搜索 | AMSG-Gym 的陌生 App 适配 |
| 长程候选比较 | 会话记忆证据分区 |
| 风险提醒 | SpecGuard 与上下文动作中的风险事实 |
| 推荐解释 | 轨迹、截图和结构化证据引用 |

因此，近期工作不应直接跳到复杂推荐系统，而应先把图谱探索、上下文动作和证据管理打牢。

### 4.4  未来评估指标

主动购物助手阶段需要增加新的评估指标：

- 购物约束满足率。
- 候选商品证据完整率。
- 推荐解释充分性。
- 错误推荐率。
- 风险商品拦截率。
- 主动澄清收益。
- 用户确认前高风险动作次数。
- 跨会话偏好复用准确率。

这些指标与现有任务完成率互补，共同衡量系统是否从“会操作 App”进一步走向“会辅助购物”。

## 5  汇报结论

本项目当前已经形成面向手机购物 App 的稳定 GUI 操作底座。其核心贡献是通过非对称权威、强 VLM 低频监督、AMSG 空间图谱、三档调度、会话记忆和机械护栏，使小型 GUI 模型能够更可靠地执行真实购物 App 的长程任务。

MobileForge 对本项目的主要启发是：将真实 App 探索、任务挖掘和分层反馈转化为 AMSG-Gym，用于陌生购物 App 的图谱冷启动和持续修复。MemGUI-Agent 对本项目的主要启发是：将上下文管理显式建模为可验证动作，用 VCA 提升长程任务中的事实保留和记忆可靠性。

在近期研究中，MobileForge 与 MemGUI-Agent 应作为现有系统优化手段，服务于购物 App 操作稳定性、泛化性和长程可靠性。主动专业购物助手是下一阶段拓展方向，应在上述底座成熟后，再引入购物意图、商品证据、决策引擎、主动策略和授权边界。
